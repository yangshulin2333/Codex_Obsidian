# Roblox 魔法杖模型制作工作流

## 定位

这是当前正式生产基线，用于把一把已确认的 Roblox RPG 魔法杖正视图，制作成可供混元 3D、TripoAI 等图生 3D 工具使用的稳定六视图。

核心目标不是让每张图单独更漂亮，而是让所有视图明确表现为**同一个物体的旋转结果**。

## 不可打破的顺序

1. 可以先生成一张包含多把法杖的效果图，只用于选型。
2. 用户选中目标后，只生成或扣取一张完整的 `front.png`。
3. 必须等待用户明确确认 `front.png`。
4. 正面确认后，计算比例、组件、材质和组件级深度。
5. 在生成任何侧向视图前，Codex 必须主动询问 `left.png`、`right.png`、`left45.png`、`right45.png` 各自必须看见与隐藏的结构，并复述数量、位置和遮挡关系。
6. 必须等待用户逐项确认侧向可见性合同；不能用“是否对称”代替这一步，也不能从正视图自行推断。
7. 按已确认的合同生成并审核 `left45.png`，用它建立该观察方向的深度证据。
8. 同时参考 `front.png + left45.png` 生成严格 90° 的 `left.png`。
9. 按各自合同生成并审核 `right45.png` 和 `right.png`。只有用户明确授权某一目标文件可以由某一已接受文件镜像时才允许镜像，并记录授权。
10. 最后生成 `back.png`。
11. 制作六视图 contact sheet，通过检查后才进入上传目录。

**在用户确认 `front.png` 之前，禁止生成 45°、侧面或背面。**

## 默认交付视图

```text
front.png
back.png
left.png
right.png
left45.png
right45.png
```

默认不生成 `top.png` 和 `bottom.png`。只有二维参考时，轴向结构没有可靠证据，强行生成容易虚构零件并污染图生 3D 输入。

## 阶段 A：效果图筛选

- 一张效果图可以展示多把独立法杖。
- 每把必须完整、互不遮挡、尺寸接近、正面朝向一致。
- 设计应有明显差异，但组件复杂度要适合图生 3D。
- 效果图不是多视图基准，不能直接把其中的模糊小图当最终 `front.png`。
- 用户选中后，再单独生成或扣取该法杖的高清正面。

## 阶段 B：正视图确认

`front.png` 是唯一设计基准，必须满足：

- 单把法杖，完整可见，四周有安全留白。
- 不触边、不裁切、不混入相邻法杖像素。
- 无文字、标签、水印、UI、背景场景和魔法特效。
- 顶部、托架、杖身、金属环和尾部均清晰。
- 用户已经明确确认造型、比例、颜色和材质。

如果从效果图扣取，固定列宽只能用于定位，最终边界必须根据前景轮廓计算，并增加安全留白。前景距离边缘小于 8px 或任何零件被截断时硬拒绝。

## 阶段 C：比例与结构锁

把物体总高定义为 `100%`，记录：

- 顶部主元素占比。
- 托架 / 固定结构占比。
- 上部和下部金属环的位置与高度。
- 杖身占比、直径和锥度。
- 尾部占比、宽度和形状。
- 正面最大宽度。

固定组件必须逐项列出。不同视图里不能增加、删除、替换或换色。

画布尺寸不作为绝对规范。当前内置图片生成常用 `1024x1536` 竖图；所有视图必须使用同一画布、同一等比缩放和接近一致的上下留白。禁止横向压缩来伪造侧视图。

## 阶段 D：组件级深度合同

不要再用“侧视宽度占整杖高度的固定百分比”作为通用目标。按组件分别记录：

| 组件 | 正面宽度 | 预期侧面深度 | 几何依据 |
|---|---:|---:|---|
| 杖身 | `[W]` | `[Dmin-Dmax]` | 圆柱 / 椭圆 / 扁柄 |
| 主宝石 | `[W]` | `[Dmin-Dmax]` | 厚切晶体 / 球体 / 凸面体 |
| 托架 | `[W]` | `[Dmin-Dmax]` | 爪 / 叶片 / 鹿角 / 框架 |
| 尾部 | `[W]` | `[Dmin-Dmax]` | 圆帽 / 球体 / 锥体 |

常用起点：

- 圆柱杖身侧视直径约等于正面杖身宽度。
- 厚切宝石侧深可先估为正面宽度的 `45%-55%`，再由 45° 图校正。
- 托架必须保留前后叠层，不能压成针状轮廓。
- 金属环必须是完整环形体，不是贴在正面的薄片。

## 阶段 E：45° 深度桥

在生成 `left45.png` 或 `right45.png` 之前，必须先通过“侧向可见性合同门禁”。Codex 必须主动向用户询问并复述四个输出文件各自的：

- 相机观察方向和文件名映射。
- 必须看见的结构。
- 必须隐藏或被遮挡的结构。
- 单侧细节的准确数量、所在位置和前后遮挡关系。
- 该方向应表现的组件厚度与连接关系。

用户未明确确认时停止生成，并标记 `SIDE_VISIBILITY_CONTRACT_MISSING`。不得先问“它是否对称”并据此决定镜像；即使外观疑似相同，四个文件仍是四份独立输出合同。

`left45.png` 只允许把同一物体水平旋转 45°：

- 零俯仰、零翻滚、正交投影。
- 保持组件数量、纵向锚点、颜色、材质和总高。
- 清楚表现宝石、托架、杖身、金属环和尾部的前后厚度。
- 任何零件漂移或新增都拒绝。

45° 图通过后才允许生成 90° 侧视图。

## 阶段 F：严格 90° 侧视

`left.png` 必须同时参考已接受的 `front.png`、`left45.png` 和用户确认的 `left.png` 可见性合同，相当于在 45° 基础上继续水平旋转 45°。

侧视图有两道独立门禁：

1. **角度门禁**：必须是垂直 90°，不是 80°、右前方或 3/4 视角。
2. **体积门禁**：严格侧面不等于纸片。杖身、宝石、托架、金属环和尾部必须保留合理厚度。

拒绝代码：

```text
SIDE_VIEW_NOT_90_DEGREE
SIDE_DEPTH_COLLAPSE
SHAFT_DEPTH_COLLAPSE
GEM_DEPTH_COLLAPSE
HOLDER_DEPTH_COLLAPSE
SIDE_VISIBILITY_CONTRACT_MISSING
SIDE_VISIBILITY_CONTRACT_BROKEN
UNCONFIRMED_SIDE_MIRROR
```

`left.png`、`right.png`、`left45.png`、`right45.png` 必须分别对照自己的已确认合同验收。任何必须可见结构缺失、必须隐藏结构出现，或数量、位置、遮挡关系错误，标记 `SIDE_VISIBILITY_CONTRACT_BROKEN`。

镜像不是默认路径。只有用户明确授权“目标文件可由指定来源文件镜像”后才允许执行，并在运行记录中写明来源、目标、授权内容和日期；否则标记 `UNCONFIRMED_SIDE_MIRROR`。一次授权只适用于被点名的文件，不能自动扩展到其他视图或下一件资产。

## 阶段 G：背视图

背视图在正面、45° 和侧面都稳定后生成：

- 同一轮廓、总高、厚度节奏和纵向锚点。
- 同一组件数量和材质分区。
- 背面雕刻可以简化，但不能变成另一把法杖。
- 背面整体可以接近正面轮廓，但光照和表面细节应明确表现为物体背面。

## 阶段 H：归一化与最终检查

- 所有视图使用相同画布尺寸。
- 只允许等比缩放和平移，不允许横向压缩。
- 顶部和尾部完整，四周留白一致。
- 输出 contact sheet，按 [[CHECKLIST]] 审核。
- 通过后复制 6 张图到最终上传目录。

## 当前已验证案例

- 案例：Verdant Aurora Wand，2026-07-11。
- 结构：厚凸椭圆晶体 + 四片叶状托架 + 圆柱木质杖身 + 双金环 + 圆润尾帽。
- 结果：用户确认六视图“效果非常好”。
- 当时该单例在获得用户确认后使用了成对镜像，并使用组件级深度合同。
- 边界：这是历史案例，不构成后续资产的镜像授权。新资产仍必须先确认四份侧向可见性合同，再逐图审核。
