# Roblox 魔法杖模型制作工作流 V2

> [!warning] 2026-07-11：V2 当前进入复盘与实验状态
> 本轮确认 V2 存在两个系统性问题：固定矩形裁切可能截断物体；“侧视越窄越正确”的规则会造成宝石、托架和杖身纸片化。当前执行时优先使用 [[V2.1_稳定图片实验流程]]，旧的 `6%-8% 整杖高度`侧视经验值不再作为目标。

> [!warning] 2026-08-12：侧向视图规则同步
> V2 中“先判断对称性，再决定是否镜像”是历史实验路径，不再作为默认规则。生成任何 `left/right/left45/right45` 前，Codex 必须主动询问并复述各输出的可见、隐藏、数量、位置和遮挡合同，等待用户确认。镜像仅在用户明确点名来源与目标文件时允许，并必须记录。

## 目标

把一张 Roblox 风格魔法杖参考图，整理成适合混元 3D / TripoAI 使用的多视图输入图。

核心目标不是生成更好看的插画，而是让 3D AI 更容易识别同一个道具的结构、比例、材质和厚度。

## 当前默认交付

默认只交付 6 视图：

- `front.png`
- `back.png`
- `left.png`
- `right.png`
- `left45.png`
- `right45.png`

默认不交付：

- `top.png`
- `bottom.png`

原因：如果只有 2D 正视图，正上方和正下方视角无法可靠推断。强行生成容易瞎编顶部和底部结构，反而污染混元 3D / TripoAI 的输入。

只有在已经有可靠 3D 模型、深度图、建模草图，或用户明确接受推断风险时，才单独制作 `top.png` / `bottom.png`。

## 核心原则

这是同一个物体的严格多视图，不是一组不同变体。

AI 只能旋转同一把魔法杖，不能重新设计、不能补设计、不能增加或删除零件。

每一把魔法杖都必须先确认完整的 `front.png`。正面只能锁定外观和正面比例，不能单独证明真实深度；侧面深度必须由组件级深度合同和已确认的 45°视图共同约束。

## 标准流程

### 1. 选择目标魔法杖

如果输入图是一组魔法杖，先明确编号，例如“从左往右第 3 个”。

建立单独输出目录：

```text
<asset_name>_3dai_<date>/
├─ _docs/
├─ _checks/
├─ _imagegen_candidates/
├─ 01_accepted_views/
└─ 00_final_hunyuan_upload_6view_no_top_bottom/
```

目录规则：

- `_docs/`：结构锁、比例表、最终状态。
- `_checks/`：合成检查图、bbox 测量 JSON。
- `_imagegen_candidates/`：候选图、失败图、被拒绝版本。
- `01_accepted_views/`：已经通过审核的单视图。
- `00_final_hunyuan_upload_6view_no_top_bottom/`：最终上传文件夹，只能放 6 张 PNG。

### 2. 先确认正视图

优先从原图扣出目标魔法杖作为 `front.png`，不要一开始就让 AI 重画正视图。

禁止把固定列宽矩形直接当作最终裁切结果。固定列宽只能定位目标；最终必须按前景遮罩计算完整 bbox，并增加至少 `64px` 或顶部最大宽度 `12%` 的安全边距。自动分割不可靠时，改用手工多边形遮罩 / 抠图。

只有当原图质量太低、遮挡严重、背景污染严重时，才生成新的正视图。

`front.png` 必须先通过人工确认，确认内容：

- 这把魔法杖就是用户指定的那一把。
- 顶部主元素、托架、杆身、尾部都清晰。
- 颜色和材质符合源图。
- 不是长法杖、长枪、剑、骨棒或其他武器。
- 没有多余背景、文字、水印、UI 图标。
- 鹿角、叶尖、花瓣、晶体尖端等没有触碰裁切边缘。
- 没有混入相邻魔法杖像素，画布内没有第二层明显矩形底图。

前景距离裁切边缘小于 `8px` 时硬拒绝，标记 `FRONT_CROP_TOUCHES_EDGE`。任何组件被切掉时标记 `FRONT_CROP_CLIPPED`。

没有确认正视图之前，不生成其他视图。

### 3. 计算比例锁

把整把魔法杖高度定义为 `100%`，先估算并写入 `_docs/MEASUREMENTS.md`。

必须记录：

- 画布尺寸，默认 `1024x2048`。
- 目标物体高度，推荐约 `1720px`。
- 顶部主元素占总高度百分比。
- 顶部托架 / 固定结构占总高度百分比。
- 中间握柄 / 杖身占总高度百分比。
- 底部装饰 / 尾坠占总高度百分比。
- 正面最大宽度占总高度百分比。
- 严格 90°侧面各组件的局部深度：杖身、宝石、托架、尾部。
- 45°视图最大宽度占总高度百分比。

常用范围：

- 正面宽度通常约总高度 `15%-22%`，具体看顶部装饰。
- 背面宽度应接近正面，可略窄但不能换造型。
- 不再把 `6%-8% 整杖高度`作为通用侧面目标。侧面厚度必须按宝石宽度、托架宽度和杖身直径分别计算。
- 45°视图应明显宽于正侧面，明显窄于正面。

注意：先判断相机角度是否正确，再做比例归一化。不要用缩放掩盖错误视角。

### 4. 写结构锁

在 `_docs/STRUCTURE_LOCK.md` 写清楚固定组件。

必须包含：

- 1 个顶部主元素。
- 1 个顶部托架 / 固定结构。
- 1 根握柄 / 杖身。
- 中部装饰的数量和位置。
- 金属环 / 束带数量和位置。
- 1 个底部装饰 / 尾坠。

同时写死颜色和材质：

- 顶部主元素：颜色 + 材质。
- 金属件：颜色 + 材质。
- 握柄 / 杖身：颜色 + 材质。
- 中部宝石：颜色 + 材质。
- 底部装饰：颜色 + 材质。

禁止项：

- 不添加新的翅膀、尖刺、链条、布条、藤蔓、额外宝石、魔法特效或背景装饰。
- 不删除原有组件。
- 不把某个组件换成其他形状。
- 不改变宝石、金属、木材、骨骼、水晶等材质属性。

### 5. 侧向可见性合同门禁

在生成任何 `left.png`、`right.png`、`left45.png`、`right45.png` 前，Codex 必须主动询问用户，并逐个文件复述：

- 相机从哪个方向观察，文件名如何映射。
- 必须看见哪些结构。
- 必须隐藏或被遮挡哪些结构。
- 单侧细节的准确数量和位置。
- 前后遮挡顺序、连接关系与应保留的厚度。

用户必须明确确认四份合同后才能继续。不得先问“它是否对称”并据此替用户决定，也不得从 `front.png` 自行推断镜像关系。

缺少合同标记 `SIDE_VISIBILITY_CONTRACT_MISSING`。成图违反合同标记 `SIDE_VISIBILITY_CONTRACT_BROKEN`。

镜像不是默认路径。只有用户明确说出“哪一个已接受文件可以镜像成哪一个目标文件”时才允许，并在运行记录中保存原话和日期。未经确认镜像标记 `UNCONFIRMED_SIDE_MIRROR`；一次授权不得扩展到其他视图或下一把魔法杖。

### 6. 逐个生成并审核视图

实验阶段推荐顺序：

1. `front.png`：正视图，先确认。
2. 四份侧向可见性合同：由 Codex 主动询问、复述，等待用户确认。
3. `left45.png`：按自己的合同生成左前 45°深度桥接图，先确认真实厚度和前后关系。
4. `left.png`：同时参考 `front.png`、`left45.png` 与自己的合同，生成严格垂直 90°左侧面。
5. `right45.png`：按自己的合同独立生成并审核；仅在用户明确授权时使用指定镜像来源。
6. `right.png`：按自己的合同独立生成并审核；仅在用户明确授权时使用指定镜像来源。
7. `back.png`：保持同一轮廓、同一材质区、同一组件数量。

不要一次性生成全部视图。每张图通过审核后再进入下一张。

### 7. left / right 侧视双门禁

`left.png` 和 `right.png` 必须是垂直 90°正侧面。

角度正确不等于厚度正确。侧视还必须保留非零物理体积：圆柱杖身不能缩成细线；宝石必须显示侧体或凸起；托架必须保留前后错层；尾部必须保留圆锥或圆帽体积。

如果角度错误，标记 `SIDE_VIEW_NOT_90_DEGREE`。如果角度正确但物体被压扁，标记 `SIDE_DEPTH_COLLAPSE`。不能用横向缩放修复这两类问题。

它们不是：

- 左前方 / 右前方。
- 45°视图。
- 3/4 视图。
- 为了看清细节而保留正面宽面的替代图。

硬性判定：

- 正面宝石宽面不能继续朝向相机；侧面必须显示符合深度合同的侧体、倒角或凸起，而不是彩色细线。
- 如果主宝石仍然是大面积彩色正面，就是 80°左右的斜侧视，必须拒绝。
- 托架、爪形结构、叶片结构在侧面可以重叠，但必须保留前后错层和非零厚度。
- 金属环应成为窄侧带或椭圆边。
- 正面专属装饰应变成边缘凸起，或被厚度遮挡。
- 侧视总宽度通常小于正视图和 45°视图，但不能低于组件级深度合同下限。

失败标记：

```text
SIDE_VIEW_NOT_90_DEGREE
SIDE_DEPTH_COLLAPSE
SIDE_VISIBILITY_CONTRACT_MISSING
SIDE_VISIBILITY_CONTRACT_BROKEN
UNCONFIRMED_SIDE_MIRROR
```

### 8. 归一化和最终输出

所有通过审核的视图统一归一化：

- 画布：`1024x2048`。
- 物体高度：约 `1720px`。
- 上下边距尽量一致。
- 物体居中。
- 背景保持干净浅色或透明，不要场景。

最终上传目录只能包含：

```text
front.png
back.png
left.png
right.png
left45.png
right45.png
```

不能放入：

- 候选图。
- 检查图。
- 合成图。
- 提示词。
- 测量 JSON。
- 失败版本。
- `top.png` / `bottom.png`。

### 9. 最终检查

最终必须生成一张 contact sheet，并记录 bbox 比例。

检查项：

- 6 张图高度一致。
- 正面、背面、侧面、45°视图是同一把魔法杖。
- 组件数量一致。
- 颜色和材质一致。
- `left.png` / `right.png` 是垂直 90°侧面。
- `left45.png` / `right45.png` 才是斜侧视。
- 没有文字标签、水印、UI 图标或背景场景。

最终状态写入 `_docs/FINAL_6_VIEW_STATUS.md`。

## 一把一把生成时的节奏

如果是一组魔法杖，从左到右逐个处理。

每一把都重复：

1. 扣出完整正视图并通过触边门禁。
2. 写比例锁、结构锁和组件级深度合同。
3. Codex 主动询问并复述四份侧向可见性合同，等待用户确认。
4. 按合同生成并审核 `left45` 深度桥接图。
5. 同时参考 `front + left45 + left 合同` 生成严格 90° `left`。
6. 按各自合同生成并审核 `right45/right`；镜像仅在用户明确授权时使用并记录。
7. 生成并审核 `back`。
8. 等比例归一化，禁止横向压缩。
9. 生成 contact sheet 和最终上传目录。

不要把上一把魔法杖的装饰、颜色或材质迁移到下一把。

可以复用流程、文件结构、提示词和检查脚本，但不能复用组件内容。

## 当前经验结论

- top / bottom 在只有 2D 参考图时不稳定，默认不交付。
- left / right 既可能偏成 80°或45°，也可能被压成纸片，两类问题都必须审核。
- 整杖 bbox 宽高比只能作为异常提示，不能代表角度或真实厚度。
- 侧视不能以“越窄越好”为目标；必须符合组件级深度合同。
- 45°视图是深度桥接证据，负责锁定宝石、托架和杖身的前后关系。
- 左右观察结果不能只靠正视图判断；四个侧向输出必须先由用户确认各自可见性合同。
- 镜像属于一次性的用户授权操作，不属于默认生成规则。
