# Roblox 魔法杖 V2.1 稳定图片实验流程

## 当前定位

本页优先级高于 V2 中旧的裁切规则、视图生成顺序和侧视宽度经验值。

当前状态为 `Review / 实验中`，目标是先解决两个重复出现的失败：

1. `FRONT_CROP_CLIPPED`：正视图在拆分阶段被切掉。
2. `SIDE_DEPTH_COLLAPSE`：90°侧视角度正确，但宝石、托架或杖身被压成纸片。

2026-08-12 同步规则：本页属于历史实验流程，但不得把当时的“仅对称结构镜像”分流带回当前执行。所有侧向视图必须先通过用户确认的可见性合同；镜像只接受用户对具体来源和目标文件的明确授权。

在连续 3 把不同结构的魔法杖通过完整试跑前，不把本流程标记为稳定版。

## 已确认根因

失败证据：

- ![[evidence/2026-07-11/front-crop-clipped.png]]
- ![[evidence/2026-07-11/side-depth-collapse.png]]

### 正视图被切掉

失败不是归一化造成的，而是发生在归一化之前：用固定列宽或手写矩形从效果图中分割单把魔法杖时，越界的鹿角、叶片、花瓣或晶体已经被裁掉。后续居中、放大和 bbox 检测无法恢复丢失像素。

### 左右视图过扁

V2 把“严格 90°侧视”错误地近似成“越窄越正确”，并使用“侧视最大宽度约为整杖高度 6%-8%”作为通用目标。

这个指标对细长法杖不可靠：整杖高度主要由长杆贡献，不能代表顶部宝石、托架和圆柱杖身的真实深度。提示词中的 `collapse into a thin edge` 也进一步诱导模型把立体物体压成薄片。

### 深度证据不足

正视图只能锁定 `X / Y` 轮廓，不能可靠说明 `Z` 轴厚度。直接从正面生成 90°侧面时，模型只能在“仍显示正面宽面”和“完全压扁”之间猜测。

## 新的主流程

```text
源效果图
  -> 完整物体扣图 / 安全裁切
  -> front 完整性门禁
  -> 组件级深度合同
  -> Codex 主动询问并复述四份侧向可见性合同
  -> 用户确认合同
  -> left45 深度桥接图
  -> 45°深度审核
  -> front + left45 共同生成 left90
  -> 90°角度门禁 + 体积门禁
  -> 按各自合同生成 right / right45（镜像仅限用户明确授权）
  -> back
  -> 归一化（只缩放整体，不改变宽高比）
  -> contact sheet + 最终上传目录
```

## 阶段 A：完整正视图提取

### A1. 保留不可变源图

- 原始效果图只读保存，不覆盖。
- 每把魔法杖先建立独立候选目录。
- 固定列宽只能用于初步定位，不能直接作为最终裁切结果。

### A2. 遮罩扣图优先

普通浅色背景效果图可先运行：

```powershell
python scripts/extract_fronts.py <source.png> <candidate_output_dir> --expected-count <数量>
```

输出只作为审核候选，包含独立 `front_XX.png`、前景遮罩、源图 bbox 叠加图、contact sheet 和 `extraction_report.json`。脚本检测失败时不能自动回退到固定列宽裁切。

背景较干净时：

1. 按背景颜色建立前景遮罩。
2. 合并同一把魔法杖的相邻前景组件。
3. 由遮罩计算完整 bbox。
4. bbox 四周增加安全边距：至少 `64px`，或顶部最大宽度的 `12%`，取较大值。
5. 将扣出的完整对象放到统一背景或透明画布。

相邻魔法杖发生重叠、阴影粘连或自动遮罩不可靠时：

- 改用手工多边形遮罩 / 抠图。
- 不允许继续缩窄矩形来躲开相邻对象。
- 宁可保留少量可清理背景，也不能切掉目标物体。

### A3. 正视图硬门禁

自动检查：

- 前景像素距离裁切边缘必须大于 `8px`；建议大于 `16px`。
- 顶部、底部、左右四个方向都要检查。
- 归一化画布中不能出现另一层明显的矩形底图边界。

人工检查：

- 对照源效果图逐件核对顶部、托架、杆身、尾部。
- 检查鹿角、叶尖、花瓣、晶体尖端是否完整。
- 检查是否混入相邻魔法杖的像素。

任一前景触边或组件缺失，标记：

```text
FRONT_CROP_TOUCHES_EDGE
FRONT_CROP_CLIPPED
FRONT_CROP_NEIGHBOR_CONTAMINATION
```

此时必须停止，不能生成其他视图。

## 阶段 B：组件级深度合同

不要再用“侧视宽度 / 整杖高度”直接决定厚度。先对每个主要组件记录局部尺寸。

### 必须记录

| 组件 | 正面宽度 | 正面高度 | 预期侧面深度 | 深度依据 |
| --- | ---: | ---: | ---: | --- |
| 杖身 | `shaft_W` | `shaft_H` | `shaft_D` | 圆柱 / 椭圆柱 / 扁条 |
| 主宝石 | `gem_W` | `gem_H` | `gem_D` | 球体 / 切割晶体 / 凸面宝石 / 薄片 |
| 顶部托架 | `holder_W` | `holder_H` | `holder_D` | 爪、叶片、鹿角、金属框 |
| 尾部 | `tail_W` | `tail_H` | `tail_D` | 圆锥、圆帽、扁坠 |

### 初始深度范围

这些是起始假设，不是最终真值：

- 圆柱木质杖身：`shaft_D = 0.80-1.05 × shaft_W`。
- 椭圆杖身：`shaft_D = 0.55-0.80 × shaft_W`。
- 扁平木板杖身：`shaft_D = 0.25-0.50 × shaft_W`。
- 球形宝石：`gem_D = 0.85-1.00 × gem_W`。
- 多面切割晶体：`gem_D = 0.40-0.70 × gem_W`。
- 凸面 / 镶嵌宝石：`gem_D = 0.20-0.40 × gem_W`。
- 叶片、鹿角或爪形托架：按结构记录前后错层，不能全部合并成一条线。

如果材质和几何类别不确定，先标记 `DEPTH_ASSUMPTION_UNCONFIRMED`，通过 45°候选验证后再锁定。

## 阶段 C：先做 45°深度桥接图

### C0. 侧向可见性合同门禁

在生成任何 `left.png`、`right.png`、`left45.png`、`right45.png` 前，Codex 必须主动询问并复述每个输出的：相机观察方向、必须看见结构、必须隐藏结构、单侧细节准确数量与位置、前后遮挡顺序，以及厚度和连接证据。用户明确确认后才能继续。

不得以“是否对称”作为默认分流，也不得从正视图推测哪两张图可以镜像。合同缺失标记 `SIDE_VISIBILITY_CONTRACT_MISSING`；输出违反合同标记 `SIDE_VISIBILITY_CONTRACT_BROKEN`。

镜像默认未授权。只有用户明确点名“来源文件 -> 目标文件”后才允许，并记录用户原话与日期；未经确认镜像标记 `UNCONFIRMED_SIDE_MIRROR`。一次授权不适用于其他文件或下一件资产。

新的推荐顺序：

1. `front.png`
2. 四份侧向可见性合同确认
3. `left45.png`
4. `left.png`
5. `right45.png`（按自己的合同；明确授权时才可镜像）
6. `right.png`（按自己的合同；明确授权时才可镜像）
7. `back.png`

`left45.png` 的作用不是装饰展示，而是补充正视图没有提供的深度信息。

审核 45°时必须确认：

- 杖身是圆柱、椭圆柱还是扁条。
- 宝石有真实厚度，镶嵌位置明确。
- 托架位于宝石前方、侧方还是后方。
- 没有增加、删除或替换组件。
- 视图确实为约 45°，不是轻微斜视。

45°深度不可信时，不能继续生成 90°侧视。

## 阶段 D：由双参考生成 90°侧视

`left.png` 必须同时参考：

1. 已确认的 `front.png`：锁定设计、比例、颜色和组件。
2. 已确认的 `left45.png`：锁定深度、前后关系和宝石厚度。

提示词核心含义应为：

```text
Rotate the accepted 45-degree view another 45 degrees to reach a true 90-degree side view.
The camera is exactly side-on, but the object must keep non-zero physical volume.
Do not flatten the gemstone, holder, shaft, or tail into paper-thin shapes.
Use the component depth contract as the target thickness envelope.
```

不要再使用没有下限约束的：

```text
collapse into a thin edge
as narrow as possible
side width 6%-8% of total height
```

## 阶段 E：90°双门禁

侧视必须同时通过两道门，缺一不可。

### 门禁 1：相机角度正确

- 看不到大面积正面宝石面。
- 左右托架不以完整正面形状展开。
- 正面专属装饰只显示边缘或被遮挡。
- 不是 80°、45°或 3/4 视图。

失败码：

```text
SIDE_VIEW_NOT_90_DEGREE
```

### 门禁 2：物体体积没有坍缩

- 圆柱杖身的侧面宽度应接近正面杖身宽度，不能缩成细线。
- 宝石必须显示符合深度合同的侧体、侧棱或凸起，不是单像素彩色线。
- 托架必须保留前后错层和真实厚度，不能全部融合成针状轮廓。
- 尾部圆锥 / 圆帽必须保留体积。
- 侧视最大宽度不能低于组件深度合同给出的下限。

失败码：

```text
SIDE_DEPTH_COLLAPSE
SHAFT_DEPTH_COLLAPSE
GEM_DEPTH_COLLAPSE
HOLDER_DEPTH_COLLAPSE
```

## 阶段 F：归一化限制

归一化只允许：

- 等比例整体缩放。
- 平移居中。
- 统一上下边距。
- 统一背景或透明底。

禁止：

- 单独横向压缩侧视图。
- 为满足目标宽度而改变宽高比。
- 用缩放掩盖错误角度或错误深度。
- 在已截断的裁切图上继续归一化。

## 复杂顶部的备用路径

对于鹿角、花瓣、卷叶、镂空托架等复杂顶部：

1. 从 `front.png` 额外裁出完整顶部特写。
2. 先生成并审核顶部 `left45` 特写。
3. 再生成顶部 `left90` 特写。
4. 顶部侧视通过后，再生成整杖侧视。

如果整杖提示词仍反复压扁顶部，可以将“顶部侧视特写 + 完整正视图 + 完整45°图”作为三参考输入。

## 失败恢复树

```text
front 不完整
  -> 重新扣图，不生成任何其他视图

left45 改设计
  -> 拒绝 left45，回到结构锁和深度合同

侧向合同未确认
  -> SIDE_VISIBILITY_CONTRACT_MISSING
  -> 停止生成，由 Codex 主动询问、复述并等待用户确认

侧向视图违反可见 / 隐藏 / 数量 / 位置 / 遮挡合同
  -> SIDE_VISIBILITY_CONTRACT_BROKEN
  -> 拒绝候选，按已确认合同重做

没有用户明确授权就镜像
  -> UNCONFIRMED_SIDE_MIRROR
  -> 拒绝候选，恢复到独立输出合同

left90 仍看到正面宽面
  -> SIDE_VIEW_NOT_90_DEGREE
  -> 强化相机角度，不压缩图片

left90 变成纸片
  -> SIDE_DEPTH_COLLAPSE
  -> 提高组件深度下限，并同时输入 front + left45

复杂顶部连续两次失败
  -> 切换顶部特写路径
  -> 仍失败则停止，不污染最终上传目录
```

## 实验通过标准

必须用至少 3 类结构试跑：

- 厚切割宝石 + 托架。
- 圆形或凸面宝石 + 圆柱杖身。
- 鹿角 / 花瓣 / 卷叶等复杂镂空顶部。

每类必须满足：

- 正视图无截断、无邻图污染。
- 45°一次或两次内锁定合理深度。
- 90°侧视同时通过角度门禁和体积门禁。
- 归一化没有改变宽高比。
- 输入混元 3D / TripoAI 后，模型没有明显纸片化或顶部缺件。

## Workflow Check

- Missing gate：V2 缺少裁切触边门禁和侧视最小厚度门禁。
- Manual/automatic boundary：自动做遮罩、bbox、触边检测和尺寸记录；人工确认组件完整性、深度合理性和 3D 结果。
- Side visibility boundary：Codex 负责主动提问和逐项复述；用户负责确认每个输出必须看见 / 隐藏的结构、数量、位置和遮挡；没有确认不得生成。
- Verification evidence：原图对照图、扣图预览、45°/90° contact sheet、组件深度表、3D 测试截图。
- Handoff impact：最终上传目录结构不变，但生成顺序和侧视判定标准改变。
- Rule/doc update：README、CHECKLIST、PROMPT_TEMPLATES、STATUS 均需引用本实验流程。
