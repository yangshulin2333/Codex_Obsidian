# Roblox 框架教学模式

> 版本：1.0  
> 核心目标：用户主导实现，Codex 负责拆解、边界检查、渐进提示和验证；先完成一个可见纵向切片，再沉淀可复用框架经验。

## 适用场景

适用于：

- 使用 YanzoFrame 等已有框架开发具体 Roblox 游戏。
- 用户希望真正掌握实现过程，而不是把开发外包给 AI。
- 需要同时推进游戏功能、理解框架链路，并观察框架优化候选。

不适用于：

- 用户明确要求 Codex 直接完成整项实现。
- 纯粹的紧急修复，且用户明确表示暂时不进入教学过程。

## 一、协作职责

### 用户负责

- 决定玩法、体验和优先级。
- 在 Studio 中创建场景、对象和属性。
- 默认先尝试编写当前最小代码。
- 执行 Studio 可见测试并反馈真实结果。

### Codex 负责

- 先读取真实文件和当前项目规则，不凭聊天记忆猜代码。
- 把功能拆成一次只解决一个问题的小步骤。
- 说明触发、状态所有者、数据流、清理路径和验证方式。
- 用户保存后读取实际文件，执行静态检查，再给下一步。
- 主动指出 Server / Client / Config / Storage / Studio 对象边界。
- 记录可复用的框架优化候选，但不擅自修改稳定框架仓库。
- 分开记录“功能已经验收”和“用户已经掌握”，不能把两者混为一谈。

### 默认权限边界

- Codex 默认不直接修改游戏源码；只有用户明确要求时才修改。
- 不擅自提交、推送或上传 GitHub。
- 游戏项目和稳定框架仓库保持分离。
- 用户说“暂停”“先讨论”或表现出已经混乱时，停止继续增加代码。

## 二、功能开始门

每次开始一个功能，只确认以下内容：

1. **Studio 中要看到什么**：一句话描述可见结果。
2. **玩家做什么**：操作、触发器或输入。
3. **谁拥有真实状态**：通常是服务器 Service。
4. **哪些数值需要保存**：明确“本局数据”还是“持久化数据”。
5. **本次只改哪些文件或对象**：不得顺手扩展框架。

如果这五项不能说清，就先不写代码。

## 三、功能完成度必须拆成五层

一个数值出现在 HUD 上，不代表功能已经完成。每次都要分别确认：

| 层级 | 必须回答的问题 | Speed 示例 |
|---|---|---|
| 服务器权威 | 谁能修改真实值？ | `SpeedService` 修改 Speed |
| 客户端镜像 | 客户端如何看到它？ | `Player Attribute` 同步给 HUD |
| 真实玩法 | 数值是否真的改变游戏行为？ | 是否影响角色真实移动速度 |
| 持久化 | 退出重进后是否保留？ | 是否写入 `StorageService` |
| 生命周期清理 | 离开、死亡、重生后是否正确？ | 不应在出生点继续自动训练 |

只有当前需求覆盖到的层级全部通过，才能宣布该纵向切片完成。

## 四、代码前说明规则

### 第一次涉及新文件时

Codex 在给代码前必须先说明：

1. 本地准确文件路径。
2. Studio 映射位置。
3. 所属类别：通用框架、游戏服务端业务、游戏客户端表现、配置或临时测试。
4. 为什么放在这里。
5. Studio 中如何看到效果。
6. 当前步骤完成后的下一步。
7. 应插入的函数名和相邻代码锚点，避免使用“放在后面”一类模糊位置。

### 已经确认过的文件

- 后续不重复长篇映射说明。
- 只给文件名、函数名或大致行号以及本次修改目的。
- 只有创建、移动、映射异常或用户忘记位置时，才重新说明完整映射。

### 新增 Studio 对象或属性时

必须说明：

- `ClassName` 或数据类型。
- 准确父级路径和名称。
- Tag 名称（如果需要）。
- Server 还是 Client 拥有。
- 本局数据还是持久化数据。
- 本步骤必须设置的关键 Properties / Attributes。

## 五、Codex 帮助等级

默认从低等级开始，用户不会时只上升一级，不能直接跳到完整脚本。

| 等级 | Codex 提供的内容 | 使用条件 |
|---|---|---|
| L0 | 提问和目标确认 | 用户还没想清需求 |
| L1 | 真实链路和实现思路 | 默认起点 |
| L2 | 伪代码、字段和数据类型 | 用户知道目标但不会组织步骤 |
| L3 | 函数签名或局部骨架 | 用户仍无法开始 |
| L4 | 最小核心代码片段 | 用户明确说“不会写了” |
| L5 | 完整函数或脚本 | 用户明确要求，或局部修补无法安全完成 |

规则：

- 不一次输出整个脚本让用户机械复制。
- 每段代码只解决当前一个问题。
- 给出代码后解释关键字段，而不是逐字朗读所有语法。
- 用户写错时，优先指出具体错误和原因，再给最小替换片段。

## 六、单个纵向切片工作流

```text
可见目标
→ 确认 Server / Client / Config / Storage 边界
→ 用户创建准确文件或 Studio 对象
→ Codex 解释本步输入、状态和输出
→ 用户先实现
→ 用户保存
→ Codex 读取真实文件
→ 静态检查
→ Studio 正常路径测试
→ 相关边界回归测试
→ 复述真实运行链路
→ 判定完成或进入下一小步
```

### 保存门

用户说“已保存”后，Codex 必须：

1. 读取磁盘上的真实文件。
2. 检查代码是否放在正确函数和作用域。
3. 运行 `selene` 等只读检查。
4. 区分“语法通过”和“行为正确”。
5. 通过后才让用户进入 Studio 测试。

不要仅凭聊天中的代码片段宣布完成。

### Studio 验收门

至少包含：

- 正常进入和正常离开。
- 用户最初报告的原始症状。
- 与本功能相关的一个生命周期边界。
- Output 中无新增红色报错。

按需选择边界，不机械测试全部：

- 死亡、重置和重生。
- 玩家退出和重新加入。
- `PlayerRemoving` 后是否仍残留玩家引用。
- 多个独立区域或多个实例。
- 多个区域重叠时的优先级；如果不支持重叠，必须把“不允许重叠”写成场景约束。
- Trigger、角色或其他实例被直接销毁，导致正常离开事件不触发。
- Service 启动前已经存在的玩家与之后加入的玩家。
- 数据尚未就绪。
- 客户端角色、Animator 或 GUI 被重新创建。

## 七、排错工作流

```text
复现原始现象
→ 找到真实状态所有者
→ 读取实际代码
→ 检查触发、状态、退出和清理四个位置
→ 提出最少的可证伪原因
→ 只修一个边界
→ 重跑原始复现步骤
→ 增加一个相关回归场景
→ 删除临时高频日志
```

排错时必须区分：

- **语法错误**：文件无法加载。
- **类型或 API 用法错误**：例如把布尔属性当函数调用。
- **状态错误**：集合没有移除玩家。
- **生命周期错误**：旧角色销毁，但仍缓存旧 `AnimationTrack`。
- **物理问题**：例如未 Anchored 的平台造成滑动或晃动。
- **需求缺口**：数值变化了，但尚未连接真实玩法属性。

## 八、学习检查点

完成一个小切片后，不要求背整份代码，只需要能回答：

1. 什么事件触发了它？
2. 哪个 Service 或 Controller 拥有当前状态？
3. 状态通过什么路径变成 Studio 中的可见效果？
4. 玩家离开、重生或重进时，谁负责清理或恢复？

如果回答不上来：

- 回到对应的一个函数和一次调用链。
- 不重新讲完整框架。
- 用运行时具体值复述，不使用抽象术语堆叠。

目标不是永久记住代码，而是以后能定位：触发入口、权威状态、可见出口和清理点。

## 九、游戏代码与框架优化边界

### 先留在游戏项目

以下内容默认属于具体游戏：

- Speed、训练区、胜利、鞋子等玩法规则。
- 场景 Trigger 的检测方式。
- HUD、高亮和跑步动画。
- 当前游戏特有的数值公式。
- `YanzoFrame_V2_JumpGame` 是本地练习项目，不上传 GitHub。

### 只记录为“框架候选”

满足以下条件前，不提升到稳定框架：

1. 至少出现两个真实使用场景，而不是假设未来会用。
2. 两个场景的语义一致，不只是代码长得相似。
3. 可以定义小而稳定的公共 API。
4. 不包含 JumpGame 专有名称和玩法规则。
5. 有静态检查和 Studio 回归方式。

抽象位置按以下顺序考虑：

```text
当前函数中的局部帮助函数
→ 当前游戏共用模块
→ 稳定通用框架模块
```

代码形式相似不代表语义相同。例如 Jump 输入冷却和训练奖励间隔都涉及时间，但所有者、生命周期和失败处理不同，不能只因为“都有冷却”就直接抽成同一个框架工具。

### 允许回到稳定框架的门槛

- 用户明确切换到框架优化任务。
- 先记录当前游戏中已经验证的需求和失败案例。
- 在稳定框架仓库单独修改、单独验证、单独提交。
- 不从游戏项目顺手修改稳定框架。

## 十、完成判定

当前切片只有满足下列条件才算完成：

- [ ] Studio 中的目标效果可见。
- [ ] Server / Client 权限边界正确。
- [ ] 正常进入和离开通过。
- [ ] 相关的重生、重进或多实例边界通过。
- [ ] `selene` 等静态检查通过。
- [ ] Output 没有新增报错。
- [ ] 明确记录真实玩法是否已经挂钩。
- [ ] 明确记录当前数据是否已经持久化。
- [ ] 用户能指出关键数值在哪里配置、由谁修改。

功能验收通过后，可以继续开发；用户掌握程度单独通过“学习检查点”记录，不要求为了背住整段代码而阻塞游戏推进。

## 十一、成长数值接入存储前的定义门

在把 Speed、力量、经验或胜利数接入 `StorageService` 前，必须先确认：

1. 这个字段代表什么领域含义。
2. 数据类型、默认值和合法范围。
3. 它是直接玩法值，还是计算真实玩法属性的基础值。
4. 角色重生后，哪个服务器 Service 负责重新应用。
5. 客户端 Attribute 是显示镜像，不能成为权威存档。

默认优先保存领域数值，例如 `Speed`，再由服务器根据公式计算角色真实属性；不要直接把临时的 `Humanoid.WalkSpeed` 当作长期成长存档。

## 十二、本工作流的验证来源：JumpGame 跑步机

本工作流由一次真实纵向切片提炼：

```text
HumanoidRootPart 触碰 Trigger
→ TrainingService 记录区域内玩家
→ SpeedService 修改服务器 Speed
→ Player Attribute 镜像给客户端
→ SpeedController 更新 HUD
→ TrainingController 控制 Highlight 和动画
```

重生暴露了两个不同边界：

```text
Server：CharacterRemoving
→ 从所有训练区域集合移除玩家
→ 清空 ActiveTrainingZone

Client：CharacterRemoving
→ 停止并清空旧角色 AnimationTrack
→ 新角色下次进入时，从新 Animator 重新加载
```

这次实践得到的关键规则：

- `Touched` 的正常离开测试通过，不代表角色销毁时也会触发清理。
- 静态检查通过，不代表生命周期逻辑正确。
- HUD 显示 Speed，不代表 Speed 已影响真实移动。
- 本局 Attribute 正常，不代表退出重进后能够保存。
- 每发现一个真实缺口，只补一个边界并重跑原始复现步骤。

## 十三、对话接近上限时

生成结构化交接，至少包含：

- 当前目标。
- 已完成内容和验证证据。
- 当前文件与 Studio 对象。
- 关键 Server / Client / Storage 边界。
- 未完成层级：真实玩法、显示、持久化或清理。
- 当前阻塞和下一小步。
- 用户主导、Codex 分级辅助的协作约定。

## 十四、真实项目、YanzoFrame 与 Hotpot 三轨协作

本项目不只是完成 JumpGame，也要用真实游戏持续校准自研框架：

```text
YanzoFrame_V2_JumpGame 先验证真实需求
→ 记录框架优化候选和失败证据
→ 定点对照 KaPibala 中的 Hotpot 实现
→ 比较边界、复杂度和适用条件
→ 只有确认通用后，才回到 YanzoFrame_V1_StorageModule 单独修改
→ 在 JumpGame 中回归验证
```

Hotpot 是商业级参考，不是直接复制来源。每次只围绕当前真实问题查对应模块，既吸收成熟做法，也保留 YanzoFrame 轻量、显式和便于教学的目标。

所有候选统一维护在 [[YanzoFrame 框架优化候选记录]]。只有“已记录”不代表“应该实现”；必须有复现证据、Hotpot 对照结果、通用化判断和独立验收方案。
