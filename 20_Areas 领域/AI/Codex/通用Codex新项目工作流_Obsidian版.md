# 通用 Codex 新项目工作流

这份笔记是给以后所有新项目用的，不绑定某一个具体项目。

## 一句话原则

**不要把项目真相放在聊天记录里，要放在项目文件里。**

聊天记录适合推进当前任务，但不适合长期保存项目状态。  
真正可靠的项目状态，应该放在几个固定的 Markdown 文件里。

## 这套工作流解决什么问题

当项目越做越长，Codex 容易遇到这些问题：

- 上下文太长，开始混淆旧版本和新版本
- 新开对话后，不知道项目现在做到哪了
- Codex 不知道哪些文件能改、哪些不能改
- 功能做完了，但没有记录有没有测试通过
- 下一次继续时，要重新解释很多东西

这套工作流的目的就是：

```text
让任何一个新的 Codex 对话，都能快速接手项目。
```

## 最小文件组合

一个新项目，建议至少准备这 4 个文件：

```text
README.md
AGENTS.md
CURRENT_STATE.md
NEXT_STEPS.md
```

如果项目稍微复杂，再加：

```text
TESTING.md
DECISIONS.md
```

## 每个文件是干什么的

### README.md

给人看的项目说明。

写这些内容：

```text
这个项目是什么
怎么运行
主要目录是什么
项目当前目标是什么
```

### AGENTS.md

给 Codex 看的项目规则。

写这些内容：

```text
Codex 开始前必须先读哪些文件
主要源码目录在哪里
哪些文件可以改
哪些文件不能随便改
测试命令是什么
代码风格是什么
遇到不确定时应该先问还是先查
```

简单理解：

```text
README.md 是给人看的。
AGENTS.md 是给 Codex 看的。
```

### CURRENT_STATE.md

当前项目状态，也可以叫交接文档。

写这些内容：

```text
当前做到哪个版本
当前已验证的功能是什么
哪些改动还没测试
最近改了哪些文件
当前正在做什么
下一步最安全的动作是什么
```

这个文件最重要。  
新开 Codex 对话时，优先读它。

### NEXT_STEPS.md

下一步计划。

只写最近 3 到 5 件事，不要写太长。

推荐格式：

```text
P0：必须先做
P1：做完 P0 后再做
P2：以后再说
```

### TESTING.md

测试方法。

写这些内容：

```text
怎么启动项目
怎么运行测试
怎么手动验证
什么结果算通过
常见失败现象是什么
```

如果是游戏、前端、Roblox、App 项目，`TESTING.md` 特别重要，因为很多东西不能只靠命令行验证。

### DECISIONS.md

重要决策记录。

写这些内容：

```text
为什么选这个技术方案
为什么不做某个方向
哪些坑已经踩过
哪些规则以后不要反复讨论
```

这个文件不是每天都更新，只记录重要决定。

## 新项目第一步怎么做

新项目不要一上来就让 Codex 写代码。

第一步应该让 Codex 先读项目、建地图。

可以这样发：

```text
请先阅读当前项目目录，不要改代码。

请先输出：
1. 这个项目是什么
2. 主要目录分别干什么
3. 哪些文件是入口
4. 哪些文件是核心逻辑
5. 如何运行 / 构建 / 测试
6. 当前最大的风险是什么
7. 下一步最小安全动作是什么

然后帮我创建适合这个项目的 README.md、AGENTS.md、CURRENT_STATE.md、NEXT_STEPS.md。
```

## 每次开始一个新功能

不要直接说“继续做”。  
最好让 Codex 先确认项目状态。

可以这样发：

```text
请先读取 README.md、AGENTS.md、CURRENT_STATE.md、NEXT_STEPS.md。
先不要改代码。

请先回答：
1. 当前已验证的基线是什么？
2. 当前有没有未验证改动？
3. 本轮目标是什么？
4. 预计要改哪些文件？
5. 哪些边界不能碰？
6. 下一步最小安全动作是什么？

确认后再开始实现。
```

## 每个功能怎么推进

推荐固定顺序：

```text
1. 明确本轮目标
2. 明确不做什么
3. 找到要改的文件
4. 小范围实现
5. 运行测试
6. 修复问题
7. 更新 CURRENT_STATE.md
8. 更新 NEXT_STEPS.md
9. 必要时更新 TESTING.md / DECISIONS.md
```

重点是：

```text
每轮只做一个清楚的功能。
不要一轮里又重构、又加功能、又改 UI、又改数据结构。
```

## 功能结束时让 Codex 做什么

每个功能结束后，让 Codex 更新交接信息。

可以这样发：

```text
请收尾本轮工作。

请做：
1. 总结本轮改了哪些文件
2. 总结实现了什么
3. 说明哪些测试已经通过
4. 说明哪些还没验证
5. 更新 CURRENT_STATE.md
6. 更新 NEXT_STEPS.md
7. 如果有新测试方法，更新 TESTING.md
8. 给出下一轮建议
```

## 什么时候换新对话

不要按时间换。  
按项目状态换。

适合换新对话的时机：

```text
一个功能已经完成
测试结果已经记录
CURRENT_STATE.md 已经更新
NEXT_STEPS.md 已经更新
下一轮要做的是新功能
```

不适合换新对话的时机：

```text
功能做到一半
bug 还没修完
测试失败原因还在排查
刚发了截图或报错，还没处理完
Codex 刚理解了复杂上下文
```

简单规则：

```text
功能没闭环，不换对话。
功能已闭环，可以换对话。
```

## 新对话接手提示词

以后新开对话，可以直接用这个：

```text
请接手这个项目，但先不要改代码。

请先读取：
1. README.md
2. AGENTS.md
3. CURRENT_STATE.md
4. NEXT_STEPS.md
5. TESTING.md，如果存在
6. DECISIONS.md，如果存在
7. 当前 git status / git diff，如果项目使用 Git

然后先回答：
1. 当前项目做到哪了？
2. 当前已验证的基线是什么？
3. 当前有没有未验证改动？
4. 下一步最小安全动作是什么？
5. 哪些文件或系统边界不能碰？

等我确认后，再开始实现。
```

## 文件模板

### AGENTS.md 模板

```md
# Codex 项目规则

## 项目性质

这个项目是：<一句话说明项目>

## 开始任务前必须做

Codex 在改代码前必须先读：

1. README.md
2. CURRENT_STATE.md
3. NEXT_STEPS.md
4. TESTING.md，如果存在
5. DECISIONS.md，如果存在

然后先说明：

- 当前已验证状态
- 当前目标
- 预计改哪些文件
- 哪些地方不能碰

## 主要目录

```text
src/          源码
docs/         文档
tests/        测试
```

## 修改规则

- 优先小范围修改
- 不做无关重构
- 不删除用户已有改动
- 不确定时先读文件和搜索，再判断
- 涉及数据结构、支付、权限、安全逻辑时先说明风险

## 测试命令

```bash
<这里写测试命令>
```

## 禁止事项

- 不要改：<重要文件或目录>
- 不要做：<当前阶段不做的方向>
```

## 小项目和大项目怎么选

### 小项目

只需要：

```text
README.md
CURRENT_STATE.md
```

### 中等项目

建议：

```text
README.md
AGENTS.md
CURRENT_STATE.md
NEXT_STEPS.md
TESTING.md
```

### 长期项目

建议：

```text
README.md
AGENTS.md
CURRENT_STATE.md
NEXT_STEPS.md
TESTING.md
DECISIONS.md
每个版本的 handoff 文件
```

## 最重要的习惯

每次让 Codex 做事，都尽量让它先回答这 5 个问题：

```text
1. 当前基线是什么？
2. 本轮目标是什么？
3. 哪些文件会被改？
4. 哪些边界不能碰？
5. 怎么验证算完成？
```

如果这 5 个问题答不清楚，就不要急着让它写代码。

## 我的推荐默认流程

以后新项目就按这个来：

```text
第 1 步：让 Codex 读项目，不改代码
第 2 步：让 Codex 生成 README / AGENTS / CURRENT_STATE / NEXT_STEPS
第 3 步：确认第一轮最小目标
第 4 步：实现一个小功能
第 5 步：测试
第 6 步：更新 CURRENT_STATE
第 7 步：功能闭环后再换新对话
```

记住一句话：

```text
先建项目记忆，再让 Codex 干活。
```
