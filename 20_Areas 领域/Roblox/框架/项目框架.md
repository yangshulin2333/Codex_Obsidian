# Roblox 专业项目架构知识点整理

## 一、核心理念：结构决定项目上限

这份笔记的核心不是“某个文件夹应该叫什么”，而是一个更重要的思想：

**Roblox 项目越复杂，越需要提前设计清晰的目录结构和代码边界。**

新手常见问题是：

- 所有代码都塞进 `ServerScriptService`
- 所有客户端逻辑都混在 `StarterPlayerScripts`
- RemoteEvent 手动乱建
- UI 逻辑写在一堆 LocalScript 里
- 数据、配置、表现、服务端验证混在一起

专业做法是把项目拆成几个清晰层级：

1. **Shared（共享层）**：客户端和服务端都能访问的配置、类型、工具模块。
2. **Client（客户端）**：只负责输入、UI、视觉表现、本地反馈。
3. **Server（服务端）**：负责数据、安全验证、核心游戏规则。
4. **Packages（包）**：放通用第三方库或可复用模块。

简单说：  
**客户端负责体验，服务端负责规则，共享层负责通用定义。**

---

## 二、推荐项目结构

一个较专业的 Roblox 项目可以按下面思路组织：

```text
ReplicatedStorage
├─ Shared
│  ├─ Services
│  ├─ Classes
│  ├─ Modules
│  └─ Packages
│
├─ Assets
│  ├─ Models
│  ├─ VFX
│  ├─ Sounds
│  └─ UI
│
ServerScriptService
├─ Server
├─ Services
├─ Classes
└─ Data

StarterPlayer
└─ StarterPlayerScripts
   └─ Client

StarterGui
└─ UI
```

### 重点理解

- `ReplicatedStorage` 中的内容客户端可以看到，所以不要放服务端核心逻辑。
- `ServerScriptService` 中的内容客户端看不到，适合放数据验证、存档、核心逻辑。
- `Assets` 用来集中放模型、特效、音效、UI 模板。
- `Packages` 用来放第三方库，例如 Signal、Janitor、Sift 等。

## 三、Services：用服务拆分游戏系统

### 1. 什么是 Service

**Service（服务）**就是一个独立系统，负责游戏中的一个具体功能。

例如：

- `InventoryService`：背包系统
- `ShopService`：商店系统
- `BuildService`：建造系统
- `EnemyService`：敌人系统
- `DataService`：玩家数据系统

每个 Service 只做一件大事，不要把多个系统混在一起。

### 2. Service 的基本规则

- 一个 Service 对应一个明确职责。
- Service 通常是单例，不需要反复 `new`。
- 大多数 Service 应该提供 `Init()` 函数。
- 启动脚本统一调用所有 Service 的 `Init()`。
- 不要在 ModuleScript 顶层直接执行复杂启动逻辑。

### 3. 推荐写法

```lua
local InventoryService = {}

function InventoryService.Init()
    -- 初始化背包系统
end

function InventoryService.AddItem(player, itemId)
    -- 添加物品逻辑
end

return InventoryService
```

这种结构清楚，方便后期维护。

## 四、启动脚本：Client 和 Server 保持很薄

专业项目通常会有两个启动入口：

```text
StarterPlayerScripts
└─ Client

ServerScriptService
└─ Server
```

### Client 的职责

客户端启动脚本主要负责：

- 加载客户端控制器
- 初始化 UI
- 监听玩家输入
- 处理本地视觉反馈

### Server 的职责

服务端启动脚本主要负责：

- 加载服务端 Service
- 初始化数据系统
- 初始化远程通信
- 启动核心游戏规则

### 关键原则

启动脚本不要写太多业务逻辑。  
它应该像“总开关”，只负责启动各个模块。

## 五、Networking：不要相信客户端

Roblox 开发中最重要的安全原则：

**永远不要相信客户端。**

客户端不能直接命令服务端：

```text
我已经建造了这个物体
```

客户端应该请求服务端：

```text
我可以在这里建造这个物体吗？
```

然后服务端检查：

- 玩家距离是否合法
- 坐标是否合法
- 冷却时间是否结束
- 玩家是否拥有该物品
- 是否会穿模或越界
- 数据是否真实

验证通过后，服务端才执行逻辑。

### 推荐通信思路

```text
Client 发起请求
↓
RemoteEvent / RemoteFunction
↓
Server Service 验证
↓
修改真实数据或世界状态
↓
同步结果给 Client
```

在你当前项目中，这个思想可以继续沿用已有架构：

```text
RemoteManager 创建 RemoteEvent
DataService 做服务端验证和数据修改
PlayerDataUpdate 通知客户端刷新 UI
Controller 只负责显示和请求
```

## 六、不要手动乱建 RemoteEvent

视频中提到的一个重点是：  
不要在 `ReplicatedStorage` 里手动创建一堆 RemoteEvent，然后到处 `WaitForChild()`。

问题是：

- 名字容易写错
- 层级越来越乱
- 团队协作时容易冲突
- Rojo / Git 管理时 diff 很难看
- 逻辑分散，不好排查

更好的方式是：

- 统一用代码生成 RemoteEvent
- 用一个 Remote 管理模块集中维护名称
- 客户端和服务端都从同一个配置读取 Remote 名称

这和你项目里的 `RemoteManager` 思路是匹配的。

## 七、Classes：适合可重复生成的对象

Service 适合管理系统。  
Class（类）适合管理可以被反复创建的对象。

例如：

- 一把武器
- 一个敌人
- 一个陷阱
- 一个宠物
- 一个掉落物
- 一个建造物

### Service 和 Class 的区别

```text
InventoryService：管理整个背包系统
ItemClass：表示一个具体物品对象

EnemyService：管理敌人生成和刷新
EnemyClass：表示一个具体敌人
```

如果某个东西会出现很多份，就适合做成 Class。  
如果某个东西负责一个系统，就适合做成 Service。

---

## 八、Modules：放通用工具和配置

不是所有东西都应该变成 Service。

一些纯数据、配置、工具函数，可以放进 `Modules`。

推荐分类：

```text
Modules
├─ Core
├─ Game
├─ Math
└─ Platform
```

### 分类说明

- **Core**：底层通用工具。
- **Game**：游戏配置，比如物品表、升级表、价格表。
- **Math**：数学辅助函数，比如插值、曲线、距离计算。
- **Platform**：对 Roblox 服务的二次封装，比如 DataStore、BadgeService。

### 对你当前项目的启发

比如你的物品、装备、商店、背包配置，不应该散落在 UI 或服务里。  
更适合放在配置模块中，例如：

```text
EquipmentConfig
ShopConfig
GameConstants
```

这样 UI、服务端验证、商店系统都能引用同一份规则。

---

## 九、Assets：集中管理非代码资源

`Assets` 用来放不是代码的资源。

例如：

- 模型 `Models`
- 特效 `VFX`
- 音效 `Sounds`
- UI 模板 `UI`
- 动画 `Animations`

代码中需要用到这些资源时，通过 `Clone()` 复制模板。

### 好处

- 资源位置清晰
- 不会和代码混在一起
- 方便后期替换模型和特效
- 方便团队协作

## 十、UI 架构：避免 LocalScript 混乱

UI 是 Roblox 项目最容易变乱的部分。

新手常见写法是：

```text
每个按钮下面都塞一个 LocalScript
每个界面自己处理数据
UI 直接改玩家数据
```

这样后期很难维护。

### 推荐的中间方案

如果暂时不使用 React、Fusion 这类声明式 UI 框架，可以先采用模块化 UI 架构。

```text
ReplicatedStorage
└─ Shared
   └─ UI
      ├─ HUD
      ├─ Menus
      └─ InventoryMenu

StarterGui
└─ InventoryGui

StarterPlayerScripts
└─ Client
```

### UI 模块职责

- `UI.Init()`：统一初始化 UI。
- `InventoryController`：控制背包界面显示。
- `ShopController`：控制商店界面显示。
- `HUDController`：控制金币、背包容量、提示信息。

### 关键原则

UI 不应该直接决定游戏结果。  
UI 应该：

1. 展示数据
2. 响应玩家点击
3. 向服务端发送请求
4. 根据服务端返回的数据刷新界面

## 十一、Packages：不要重复造轮子

Packages 是通用第三方库，和当前游戏业务无关。

常见推荐：

### 1. Signal

代码级事件系统，可以替代很多 `BindableEvent`。

适合：

- 模块之间通信
- 状态变化通知
- 自定义事件监听

### 2. Janitor / Maid

用于清理事件连接和临时对象，防止内存泄漏。

适合：

- UI 面板关闭时清理连接
- 敌人死亡时清理事件
- 临时特效销毁时清理资源

### 3. Sift

Table 工具库，用来处理表的复制、过滤、合并等操作。

### 4. Charm

状态管理库，适合配合声明式 UI 框架。

### 5. ProfileService / DataService 类库

用于玩家数据保存和加载。

不过对你现在的阶段，不建议一次引入太多包。  
优先掌握：

```text
RemoteManager
DataService
Config
Controller
Server validation
```

等项目复杂后，再逐步引入包。

## 十二、适合你当前项目的落地建议

这份视频架构很好，但不要完整照搬。  
你现在更应该吸收它的核心原则，然后按小项目规模落地。

### 你当前更适合的顺序

```text
UI -> config -> Remote -> server -> client -> test
```

### 推荐先建立的结构

```text
ReplicatedStorage
├─ Shared
│  ├─ Configs
│  ├─ Remotes
│  └─ Modules

ServerScriptService
├─ Server
├─ Services
└─ Data

StarterPlayerScripts
└─ Client

StarterGui
└─ 对应功能 UI
```

### 暂时不用急着做的东西

- 完整 OOP 框架
- React / Fusion UI
- Wally 包管理
- 大型 Package 系统
- 复杂几何节点式架构
- 过早抽象所有功能

你现在最重要的是把每个功能做成清楚的闭环：

```text
配置定义
↓
Remote 请求
↓
服务端验证
↓
数据更新
↓
客户端刷新 UI
↓
测试检查
```

---

## 十三、总结思维

这份视频真正要教的是：

1. **不要把代码按“放哪里方便”组织，要按“职责边界”组织。**
2. **客户端负责表现，服务端负责真实规则。**
3. **配置、数据、UI、服务端逻辑要分离。**
4. **RemoteEvent 要集中管理，不要到处手动创建。**
5. **UI 只发请求，不直接改结果。**
6. **Packages 很有用，但新手阶段不要一次引入太多。**
7. **好的架构不是为了显得专业，而是为了后期不崩。**

一句话总结：

> Roblox 项目的专业化，不是从写复杂代码开始，而是从清晰的目录结构、职责分离和服务端验证开始。

## 英语学习

- **Architecture**：架构  
  例句：A clear architecture makes the project easier to maintain.  
  清晰的架构让项目更容易维护。

- **Service**：服务 / 系统模块  
  例句：InventoryService handles all inventory logic.  
  InventoryService 负责所有背包逻辑。

- **Module**：模块  
  例句：Put shared helper functions in a module.  
  把共享辅助函数放进模块里。

- **Client**：客户端  
  例句：The client handles UI and visual feedback.  
  客户端处理 UI 和视觉反馈。

- **Server**：服务端  
  例句：The server must validate every important action.  
  服务端必须验证每一个重要操作。

- **Validation**：验证  
  例句：Server-side validation prevents cheating.  
  服务端验证可以防止作弊。

- **Scalable**：可扩展的  
  例句：This folder structure is more scalable.  
  这个文件夹结构更可扩展。

- **Maintainable**：可维护的  
  例句：Small modules make the code more maintainable.  
  小模块让代码更容易维护。
