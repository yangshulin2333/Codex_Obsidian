**1. UI 和逻辑是不是都写在 FirstLoopController？**  
不应该把“所有逻辑”都写进去，但当前 `FirstLoopController` 确实同时负责两类事：

```
UI 表现逻辑：找按钮、改文字、显示错误
客户端功能逻辑：玩家点击后发 Remote 请求
```

它不负责真正业务规则。真正业务在 Server：

```
FirstLoopController
= 前台：按钮、UI、请求、显示结果

FirstLoopService
= 裁判：能不能加小齿轮、加多少、失败原因

DataService
= 数据入口：真正修改玩家数据
```

所以当前解耦是这样：

```
UI结构：FirstLoopDebugGui.model.json
通用UI挂载：UIController
Feature客户端表现：FirstLoopController
Feature服务端规则：FirstLoopService
真实数据写入：DataService
```

你觉得“不够解耦”是合理的。因为 `FirstLoopController` 里还写了 UI 节点合同、按钮绑定、Remote 请求、UI 刷新。对 FirstLoop 这种小 Debug 闭环可以接受；等正式 HUD、背包、拼装台这种复杂 UI，就应该继续拆成更细的 UI Adapter / ViewModel / Controller。

**2. context 是什么？**  
`context` 你可以理解成“框架发给每个 Controller 的工具包”。

来源在：

[ControllerRegistry.lua (line 27)](D:/AI/Codex/ToyBox/ToyboxGuardiansGame/src/StarterPlayer/StarterPlayerScripts/Client/Framework/Runtime/ControllerRegistry.lua:27)

里面大概长这样：

```
self._context = {
	Logger = Logger,
	Net = NetClient,
	Controllers = self._controllersByName,
}
```

然后 Registry 会调用：

```
controller:Init(self._context)
```

所以到 `FirstLoopController` 里：

```
function FirstLoopController:Init(context)
	self._logger = context.Logger
	self._net = context.Net
	self._uiController = context.Controllers.UIController
end
```

实际就是：

```
context.Logger = 日志模块
context.Net = NetClient
context.Controllers = 所有 Controller 的名字字典
context.Controllers.UIController = UIController 这个模块
```

为什么不直接 `require UIController`？  
因为框架希望所有 Controller 都通过 Registry 统一管理，互相引用也从 `context.Controllers` 拿。这样启动顺序、依赖关系更清楚。

**3. MountStudioTemplate 这句到底是什么**  
代码：

```
local gui, resolved = self._uiController:MountStudioTemplate(TEMPLATE_NAME, {
	Contract = FIRST_LOOP_UI_CONTRACT,
})
```

先拆语法。

`local gui, resolved = ...` 表示函数返回两个值：

```
gui = 克隆出来的 ScreenGui
resolved = 按 UI Contract 找到的节点表
```

冒号 `:` 是 Luau 的方法调用语法：

```
self._uiController:MountStudioTemplate(...)
```

等价于：

```
self._uiController.MountStudioTemplate(self._uiController, ...)
```

也就是自动把 `self._uiController` 当成第一个参数传进去。

后面的：

```
{
	Contract = FIRST_LOOP_UI_CONTRACT,
}
```

是一个 table，当作第二个参数 `options` 传进去。

所以这句实际意思是：

```
请 UIController：
1. 找到名叫 FirstLoopDebugGui 的模板
2. 克隆到 PlayerGui
3. 按 FIRST_LOOP_UI_CONTRACT 检查里面有没有指定节点
4. 返回 gui 和 resolved 节点结果
```

`FIRST_LOOP_UI_CONTRACT` 看起来写死，是因为它就是“接口合同”。  
解耦不是完全不写死，而是把“必须存在的节点名”集中写在一个地方。

例如：

```
UI 可以改颜色、位置、大小、图片
但 GrantSmallGearButton 这个按钮节点必须存在
否则 Controller 不知道绑定哪个按钮
```

这和代码接口类似：

```
函数名固定，不代表不解耦
节点合同固定，也不代表不解耦
```

**4. 入参看不懂怎么办**  
你这个学习习惯是对的：看到函数就想知道“谁传的？传了什么？返回什么？”

以后你看任何带入参的函数，都按这张“入参追踪卡”看：

```
函数名：
谁调用它：
传入参数 1：
传入参数 2：
每个参数长什么样：
返回什么：
会改什么状态：
失败会怎样：
```

拿 `MountStudioTemplate` 举例：

```
函数名：
UIController:MountStudioTemplate(templateName, options)

谁调用它：
FirstLoopController:_mountGui()

传入参数 1：
templateName = "FirstLoopDebugGui"

传入参数 2：
options = {
    Contract = FIRST_LOOP_UI_CONTRACT
}

返回：
gui = 克隆后的 ScreenGui
resolved = UIContract.Resolve 后的节点表

会改什么：
把 ScreenGui 放到 PlayerGui
```

你问“当前模板为什么是 FirstLoopDebugGui”：  
因为这里定义了：

```
local TEMPLATE_NAME = "FirstLoopDebugGui"
```

然后 UIController 会去这个路径找同名模板：

```
ReplicatedStorage
-> Game
-> UI
-> Templates
-> FirstLoopDebugGui
```

所以 `TEMPLATE_NAME` 就是模板查找 key。

**5. `_requestGrantSmallGear` 的下划线问题**  
你理解得很敏锐。`_` 不是“框架内部专用”，而是“当前模块内部方法”的约定。

在 `FirstLoopController` 里：

```
Init
Start
```

是公开生命周期方法，因为 Registry 会调用。

而：

```
_mountGui
_requestSnapshot
_requestGrantSmallGear
_setRequesting
_setCount
_setResult
_setError
```

这些是 `FirstLoopController` 自己内部用的小函数，不希望别的模块直接调用，所以前面加 `_`。

Luau 没有真正的 private，这只是团队约定：

```
不带 _：外部可以调用或框架会调用
带 _：模块内部 helper，外部不要直接调用
```
