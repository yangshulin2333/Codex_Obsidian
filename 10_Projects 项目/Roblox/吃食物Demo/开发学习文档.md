# 吃东西 Demo 开发学习文档

本文是给项目接管和学习用的开发文档。目标不是背代码，而是让你能快速回答：

```text
这个项目是什么？
代码结构怎么分？
一个功能从 UI 到服务端怎么走？
哪些系统已经可玩？
哪些系统只是占位或评审层？
以后让 AI 改代码时应该怎么控制边界？
```

## 2. 项目一句话

这是一个 Roblox “吃东西变强”复刻 Demo：

```text
玩家进入游戏
-> 吃普通 / 高资源 / VIP 食物
-> Muscle / Money / FoodCore 成长
-> 玩家可以买速度、体型、自动收集、VIP、+5K Muscle
-> 玩家可以领取奖励、转盘、使用背包 FoodCore
-> 玩家可以挑战其他玩家或 NPC
-> NPC 也会成长、巡逻、威胁玩家
-> 被 NPC 压制后可复活或接受轻量惩罚
-> 排行榜、商店、背包、规则、功能入口形成基础闭环
```

当前产品最大短板不是“功能不够”，而是：

```text
新玩家可能不知道先吃食物、再挑战弱目标、再进入 NPC / 高资源循环。
```

因此后续恢复功能开发时，优先方向仍应是：

```text
新手引导 / 目标任务第一版
```

## 3. 工程结构

### 3.1 Rojo 映射

项目入口：

```text
Replica_Demo_RojoKnit/default.project.json
```

Rojo 把本地目录映射到 Roblox Studio：

```text
ReplicatedStorage/Shared
-> Replica_Demo_RojoKnit/src/ReplicatedStorage/Shared

ReplicatedStorage/Packages
-> Replica_Demo_RojoKnit/Packages

ServerScriptService
-> Replica_Demo_RojoKnit/src/ServerScriptService

StarterPlayer/StarterPlayerScripts
-> Replica_Demo_RojoKnit/src/StarterPlayer/StarterPlayerScripts
```

学习这个项目时，先记住三条边界：

```text

ServerScriptService：只有服务端运行，负责裁判、数据、发奖、购买、NPC。
StarterPlayerScripts：每个玩家客户端运行，负责 UI、按钮、显示、输入和反馈。
```

## 4. 启动入口

### 4.1 服务端入口

```text
Replica_Demo_RojoKnit/src/ServerScriptService/EatDemoServer.server.luau
```

它负责：

```text
require 共享配置和 RemoteNames
require 所有服务端 Service
创建 ReplicatedStorage/Msg 和 ReplicatedStorage/ServerMsg
创建所有 RemoteEvent
Configure 各个 Service
PlayerAdded 时初始化玩家数据和状态
PlayerRemoving / BindToClose 时保存数据
连接 OnServerEvent
启动地图、食物、NPC、VIP 守卫等循环
```

你可以把它理解成服务端总装配文件：

```text
它不是所有逻辑的具体实现。
它负责把所有模块接起来。
```

### 4.2 客户端入口

```text
Replica_Demo_RojoKnit/src/StarterPlayer/StarterPlayerScripts/EatDemoClient.client.luau
```

它负责：

```text
require 共享配置和 RemoteNames
require 所有 ClientModules
获取服务端创建好的 RemoteEvent
调用 UIController.Create() 创建运行时 UI
Configure 各个 Controller
Start 绑定按钮和循环
连接 OnClientEvent 处理服务端返回
```

你可以把它理解成客户端总装配文件。

## 8. RemoteEvent 学习模型

先记四句：

```lua
-- 客户端发给服务端
remote:FireServer(data)

-- 服务端接收客户端
remote.OnServerEvent:Connect(function(player, data)
end)

-- 服务端发给客户端
remote:FireClient(player, result)

-- 客户端接收服务端
remote.OnClientEvent:Connect(function(result)
end)
```

重点：

```text
RemoteEvent 不是函数返回。
它是跨客户端和服务端的消息。
客户端 FireServer 后，服务端处理完通常用另一个 RemoteEvent FireClient 回包。
OnServerEvent 的第一个 player 参数由 Roblox 自动提供。
```

## 9. 奖励功能完整链路

这是最适合作为学习模板的功能。

```text
UIController 创建 RewardButton / RewardGiftButton
-> EatDemoClient 把按钮、Remote、回调打包传给 RewardController.Configure
-> RewardController.Start 绑定点击事件
-> 玩家点击按钮
-> RewardController.RequestClaim
-> rewardClaimEvent:FireServer()
-> EatDemoServer rewardClaimEvent.OnServerEvent
-> RewardService.ClaimReward(player)
-> 服务端检查冷却
-> 服务端读取 DataService 的 Muscle / Money / FoodCore
-> 服务端增加 RewardMuscle / RewardMoney / RewardFoodCore
-> 服务端刷新体型
-> sendRewardResult
-> rewardResultEvent:FireClient(player, payload)
-> EatDemoClient rewardResultEvent.OnClientEvent
-> RewardController.HandleRewardResult(result)
-> 客户端更新 UI、数值、背包、体型和反馈
```

功能掌握卡：

| 项 | 内容 |
|---|---|
| 功能名 | 领取奖励 |
| 玩家看到什么 | 奖励按钮、右上礼盒、冷却状态 |
| 客户端 Controller | RewardController |
| 服务端 Service | RewardService |
| 请求 Remote | RewardClaim |
| 返回 Remote | RewardResult |
| 改的数据 | Muscle、Money、FoodCore、RewardReadyAt |
| 配置来源 | EatDemoConfig |
| 最大风险 | 客户端不能决定奖励数量，冷却必须服务端判断 |

## 14. AI 协作方式

以后让 AI 修改项目时，不要直接说“优化整个系统”。

推荐说法：

```text
今天只改一个功能：奖励领取。
先定位相关文件，不改代码。
先画链路。
指出风险和最小修改方案。
我确认后再改。
改完展示 diff、测试项和回滚点。
```

AI 改代码时的固定边界：

```text
客户端只表达意图。
服务端负责裁判。
数据修改只在服务端。
付费和 DataStore 必须单独评审。
RemoteEvent 优先用于请求和反馈。
注释只写架构、安全、非显然逻辑。
简单赋值、按钮文案、普通 UI 不写废话注释。
```

## 17. 老板问功能时的回答模板

如果老板问“奖励功能怎么走”：

```text
奖励功能是客户端按钮触发，走 RewardClaim Remote 到服务端。
服务端 RewardService 校验冷却后修改 Muscle、Money、FoodCore。
然后通过 RewardResult 返回客户端更新 UI。
奖励数值来自 EatDemoConfig，客户端不能决定奖励数量。
```

如果老板问你还没学的功能：

```text
这个功能我还没完整追过，不敢直接给结论。
我会先按 UI、Controller、Remote、Service、Data、返回结果这条链路定位。
确认当前状态、风险点和相关文件后再给你准确结论。
```

这比乱答更专业。
