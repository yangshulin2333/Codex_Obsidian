# 0. 先建立整体理解

这两个脚本是一套完整的 Roblox 小玩法：

```text
玩家进入游戏
  ↓
服务端生成掉落物
  ↓
客户端创建 HUD
  ↓
客户端不断扫描附近有没有掉落物
  ↓
如果玩家靠近掉落物，客户端向服务端发送“我要吃这个”
  ↓
服务端验证：掉落物是否存在、玩家距离够不够、是否已经被吃
  ↓
验证通过后，服务端给玩家加 Muscle / Money
  ↓
服务端把结果发回客户端
  ↓
客户端更新 HUD，并播放声音、闪光、冲击波特效
```

这套逻辑的核心是：

```text
客户端负责：显示、检测、反馈、按钮交互
服务端负责：真实数据、校验、加钱、生成掉落物
```

这就是 Roblox 开发里最重要的原则之一：

> **客户端可以请求，但不能最终决定结果。服务端才是权威。**

# 2. 两个脚本之间怎么通信？

你这套脚本用了 6 个 `RemoteEvent`。

服务端创建：

```lua
local msgFolder = ensureFolder(ReplicatedStorage, "Msg")
local serverMsgFolder = ensureFolder(ReplicatedStorage, "ServerMsg")

local eatEvent = ensureRemoteEvent(msgFolder, "吃")
local boostEvent = ensureRemoteEvent(msgFolder, "加速")
local sizeEvent = ensureRemoteEvent(msgFolder, "尺寸")

local eatResultEvent = ensureRemoteEvent(serverMsgFolder, "EatResult")
local boostResultEvent = ensureRemoteEvent(serverMsgFolder, "BoostResult")
local sizeResultEvent = ensureRemoteEvent(serverMsgFolder, "SizeResult")
```

客户端等待：

```lua
local eatEvent = ReplicatedStorage:WaitForChild("Msg"):WaitForChild("吃")
local boostEvent = ReplicatedStorage:WaitForChild("Msg"):WaitForChild("加速")
local sizeEvent = ReplicatedStorage:WaitForChild("Msg"):WaitForChild("尺寸")

local eatResultEvent = ReplicatedStorage:WaitForChild("ServerMsg"):WaitForChild("EatResult")
local boostResultEvent = ReplicatedStorage:WaitForChild("ServerMsg"):WaitForChild("BoostResult")
local sizeResultEvent = ReplicatedStorage:WaitForChild("ServerMsg"):WaitForChild("SizeResult")
```

通信方向是：

```text
客户端 → 服务端：
Msg/吃
Msg/加速
Msg/尺寸

服务端 → 客户端：
ServerMsg/EatResult
ServerMsg/BoostResult
ServerMsg/SizeResult
```

也就是说：

|RemoteEvent|谁发|谁收|作用|
|---|---|---|---|
|`吃`|客户端|服务端|请求吃某个掉落物|
|`加速`|客户端|服务端|请求 2 倍速度|
|`尺寸`|客户端|服务端|请求体型/Muscle 加成|
|`EatResult`|服务端|客户端|返回吃掉落物结果|
|`BoostResult`|服务端|客户端|返回加速结果|
|`SizeResult`|服务端|客户端|返回尺寸结果|

# 8. 客户端第五段：常量配置

```lua
local SCAN_INTERVAL = 0.25
local EAT_RADIUS = 10
local VERSION = "v0.4.0"
```

## `SCAN_INTERVAL = 0.25`

意思是：

> 每 0.25 秒扫描一次附近掉落物。

也就是一秒扫描 4 次。

为什么不每帧扫描？

因为每帧扫描太频繁。

如果游戏是 60 FPS，每秒会扫描 60 次。

你现在用 0.25 秒一次，性能更稳。

---

## `EAT_RADIUS = 10`

意思是：

> 客户端认为玩家距离掉落物 10 studs 以内，就可以发送“吃”的请求。

注意：服务端也有一个 `EatRadius`，是 30。

服务端配置是：

```lua
EatRadius = 30
```

这意味着：

```text
客户端：10 studs 内才主动请求
服务端：30 studs 内都算合法
```

这不一定是 bug，但两个值不一致。更常见的设计是：

```text
客户端半径 <= 服务端半径
```

你现在就是这样，所以可以接受。

|---|---|
|`nearestInfo`|最近掉落物所属的配置|
|`nearestItem`|最近的掉落物模型|
|`nearestDistance`|最近距离|

`math.huge` 是无限大。

一开始距离设成无限大，后面任何真实距离都会比它小。

```lua
for _, info in ipairs(DROP_FOLDERS) do
	local folder = workspace:FindFirstChild(info.folderName)
```

`ipairs(DROP_FOLDERS)` 会按顺序遍历数组。

```lua
{ name = "掉落物", folderName = "掉落物" }
```

`_` 是索引，但你没用它，所以用 `_` 表示忽略。

`info` 是当前配置。

```lua

	for _, item in ipairs(folder:GetChildren()) do
```

## 判断是不是合法掉落物

```lua

```

意思是：

```text
1. item 必须是 Model
2. item 必须有 PrimaryPart
```

为什么要 PrimaryPart？

因为后面要用：

```lua

```

来计算掉落物位置。

## 只计算 XZ 平面距离

```lua
local rootXZ = Vector3.new(rootPart.Position.X, 0, rootPart.Position.Z)
local foodXZ = Vector3.new(item.PrimaryPart.Position.X, 0, item.PrimaryPart.Position.Z)
local distance = (rootXZ - foodXZ).Magnitude
```

这里刻意把 Y 设为 0。

意思是：

> 不管高度差，只算地面平面距离。

如果玩家在球上方或球下方，只要水平距离近，也算近。

## 更新最近掉落物

```lua

	nearestDistance = distance
	nearestInfo = info
	nearestItem = item
end
```

这是一种常见算法：

```text
先假设最近距离是无限大
遍历每一个物体
如果当前物体更近，就记录它
最后留下来的就是最近的物体
```

## 如果最近物体在可吃范围内

```lua

```

这句意思是：

```text
必须同时满足：
1. 找到了配置
2. 找到了物体
3. 距离 <= 10
```

然后生成 key：

```lua
local key = nearestInfo.name .. "/" .. nearestItem.Name
```

比如：

```text
掉落物/1
掉落物VIP/14
```

`..` 是 Lua 字符串拼接。

---

## 防重复请求

```lua
if not sentRecently[key] then
	markRecent(key)
```

如果这个掉落物最近没请求过，就标记。

然后更新 UI：

```lua

statusLabel.Text = "Request " .. lastRequestText
```

最后发送给服务端：

```lua
eatEvent:FireServer(nearestInfo.name, nearestItem.Name)
```

这句非常重要。

客户端不是直接加 Muscle，而是告诉服务端：

```text

文件夹类型 = nearestInfo.name
掉落物名字 = nearestItem.Name
```

服务端再判断能不能吃。

# 21. 客户端循环扫描

```lua
		return

	scanClock = 0

end)
```

## `Heartbeat`

`Heartbeat` 是 Roblox 每帧触发的事件。

`dt` 是上一帧到这一帧经过的时间。

比如 60 FPS 时，`dt` 大概是：


## 计时逻辑

```lua

```

意思是：

```lua
scanClock = scanClock + dt
```

不断累计时间。

```lua
if scanClock < SCAN_INTERVAL then
	return
```

如果还没到 0.25 秒，就退出。

```lua
scanClock = 0
```

到了 0.25 秒，就清零并扫描一次。

这就是：

```text
每帧检查时间
但每 0.25 秒才真正扫描一次
```

# 31. 服务端函数：`getLeaderstat`

```lua
local function getLeaderstat(player, statName)
	local leaderstats = player:FindFirstChild("leaderstats")
	if not leaderstats then
		leaderstats = Instance.new("Folder")
		leaderstats.Name = "leaderstats"
		leaderstats.Parent = player
	end

	local value = leaderstats:FindFirstChild(statName)
	if not value then
		value = Instance.new("IntValue")
		value.Name = statName
		value.Value = 0
		value.Parent = leaderstats
	end

	return value
end
```

这个函数非常重要。

作用：

> 获取玩家的某个数值。如果没有，就自动创建。

比如：

```lua
local muscle = getLeaderstat(player, "Muscle")
```

如果玩家下面没有 `leaderstats`，就创建：

```text
Player
└─ leaderstats
```

如果 `leaderstats` 下面没有 `Muscle`，就创建：

```text
Player
└─ leaderstats
   └─ Muscle
```

`Muscle` 类型是：

```lua
IntValue
```

也就是整数值。

## 为什么叫 `leaderstats`？

Roblox 有一个约定：

如果玩家下面有一个叫 `leaderstats` 的 Folder，里面的数值会显示在玩家排行榜上。

所以：

```text
leaderstats
├─ Muscle
└─ Money
```

通常会显示在右上角玩家列表里。

# 37. 服务端函数：应用体型

```lua
local function applyCharacterScale(player, scale)
	local character = player.Character
	if not character then
		return false, "Character not ready"
	end

	local ok, err = pcall(function()
		character:ScaleTo(scale)
	end)

	if not ok then
		return false, tostring(err)
	end

	return true
end
```

这个函数负责把角色整体缩放。

重点是：

```lua
local ok, err = pcall(function()
	character:ScaleTo(scale)
end)
```

## 什么是 `pcall`？

`pcall` 是保护调用。

普通代码如果报错，整个脚本可能中断。

用 `pcall` 包起来后：

```text
成功：ok = true
失败：ok = false, err = 错误信息
```

所以这里不会因为 `ScaleTo` 出错导致整个服务端脚本崩掉。

---

# 38. 服务端函数：根据 Muscle 计算体型

```lua
local function calculateBodyScale(muscleValue, muscleMultiplier)
	local safeMuscle = math.max(0, muscleValue or 0)
	local safeMultiplier = math.max(1, muscleMultiplier or 1)
	local effectiveMuscle = safeMuscle * safeMultiplier
	local bodyScale = CONFIG.DefaultBodyScale + (effectiveMuscle / CONFIG.MuscleScaleDivisor)
	return math.clamp(bodyScale, CONFIG.DefaultBodyScale, CONFIG.MaxBodyScale), effectiveMuscle
end
```

这个函数是体型成长公式。

公式是：

```text
实际 Muscle = Muscle × 倍率
身体大小 = 默认大小 + 实际 Muscle / 1500
```

因为：

```lua
MuscleScaleDivisor = 1500
```

举例：

|Muscle|bodyScale|
|--:|--:|
|0|1|
|150|1.1|
|750|1.5|
|1500|2|
|3000|3|
|3750+|3.5 上限|

`math.clamp` 限制范围：

```lua
math.clamp(bodyScale, CONFIG.DefaultBodyScale, CONFIG.MaxBodyScale)
```

意思是：

```text
最小不能小于 1
最大不能超过 3.5
```

# 39. 服务端函数：刷新体型


作用：

> 读取玩家 Muscle，根据公式计算目标体型，然后应用到角色。

关键逻辑：

```lua
local currentBodyScale = player:GetAttribute("CurrentBodyScale")
local shouldApply = typeof(currentBodyScale) ~= "number" or math.abs(currentBodyScale - bodyScale) >= CONFIG.MinScaleDelta
```

意思是：

```text
如果玩家还没有 CurrentBodyScale
或者当前体型和目标体型差距 >= 0.035
才真正调用 ScaleTo
```

为什么这么做？

因为每吃一次都立刻缩放，可能太频繁。

小变化不缩放，可以减少抖动和性能压力。

# 40. 服务端函数：延迟刷新体型

```lua
local function scheduleBodyScaleRefresh(player)
```

这个函数不是马上刷新，而是延迟刷新。

核心：

```lua
if scaleUpdateScheduledByPlayer[player] then
	return true, nil, bodyScale, effectiveMuscle, muscleMultiplier
end
```

如果已经安排过刷新，就不要重复安排。

然后：

```lua
scaleUpdateScheduledByPlayer[player] = true
task.delay(CONFIG.ScaleUpdateDelay, function()
	scaleUpdateScheduledByPlayer[player] = nil
	if player.Parent then
		refreshBodyScaleFromMuscle(player)
	end
end)
```

意思是：

```text
标记这个玩家已经安排刷新
0.45 秒后执行真正刷新
刷新前检查玩家还在不在游戏里
刷新后解除标记
```

这个设计可以防止玩家连续吃很多球时，角色疯狂 ScaleTo。

# 41. 服务端函数：加速 `activateSpeedBoost`

```lua
local function activateSpeedBoost(player)
```

这个函数由客户端点击按钮触发。

服务端绑定在这里：

```lua
boostEvent.OnServerEvent:Connect(activateSpeedBoost)
```

注意：

当客户端调用：

```lua
boostEvent:FireServer()
```

服务端函数第一个参数自动就是 `player`。

所以客户端不用传 player，Roblox 会自动传。

---

## 冷却判断

```lua
local now = os.clock()
local lastRequestAt = lastBoostRequestAtByPlayer[player] or 0
if lastRequestAt > 0 and now - lastRequestAt < CONFIG.BoostCooldown then
	sendBoostResult(player, false, "Speed cooldown", {
		active = player:GetAttribute("SpeedBoostActive") == true,
		walkSpeed = player:GetAttribute("CurrentWalkSpeed") or CONFIG.DefaultWalkSpeed,
	})
	return
end
```

这段意思是：

```text
当前时间 = now
上次请求时间 = lastRequestAt
如果距离上次请求还没超过 2 秒
就拒绝
```

`CONFIG.BoostCooldown = 2`

所以冷却时间是 2 秒。

---

## 设置加速状态

```lua
local expiresAt = now + CONFIG.BoostDuration
boostExpiresAtByPlayer[player] = expiresAt
player:SetAttribute("SpeedBoostActive", true)
player:SetAttribute("CurrentWalkSpeed", CONFIG.BoostWalkSpeed)
applyWalkSpeed(player, CONFIG.BoostWalkSpeed)
```

这里做了四件事：

```text
1. 计算过期时间
2. 记录这个玩家的加速过期时间
3. 给玩家设置属性 SpeedBoostActive = true
4. 设置当前速度为 32
```

---

## 通知客户端

```lua
sendBoostResult(player, true, "2x speed active", {
	active = true,
	walkSpeed = CONFIG.BoostWalkSpeed,
	duration = CONFIG.BoostDuration,
})
```

客户端收到后会：

```text
按钮变成 Speed 2x
状态显示 WalkSpeed 32
播放加速特效
```

---

## 8 秒后结束加速

```lua
task.delay(CONFIG.BoostDuration, function()
```

8 秒后执行里面的逻辑。

里面有两个关键判断：

```lua
if not player.Parent then
	return
end
```

如果玩家已经离开游戏，就退出。

```lua
if boostExpiresAtByPlayer[player] ~= expiresAt then
	return
end
```

这句很关键。

它防止旧的延迟任务错误覆盖新的加速状态。

比如玩家连续触发加速：

```text
第一次加速：expiresAt = 100
第二次加速：expiresAt = 105
```

如果第一次的延迟任务到时间了，它发现当前记录不是 100，而是 105，就不会结束第二次加速。

这是比较好的写法。

# 42. 服务端函数：尺寸/Muscle 翻倍

```lua
"Muscle permanently doubled"
```

```text
Double Muscle
```

或者中文：

```text
肌肉翻倍
```

```lua
if muscle.Value <= 0 then
	sendSizeResult(player, false, "Eat first, Muscle is 0", {
		permanent = true,

		multiplier = 1,
	})
	return
end
```

意思是：

> 如果还没吃过东西，Muscle 为 0，就不能翻倍。

因为：

```text
0 × 2 = 0
```

所以必须先吃东西。

# 43. 服务端核心函数：吃掉落物 `consumeDrop`

```lua
local function consumeDrop(player, resName, dropName)
```

这个函数由客户端触发：

```lua
eatEvent:FireServer(nearestInfo.name, nearestItem.Name)
```

服务端接收时，参数变成：

```lua
player = 自动传入的玩家
resName = nearestInfo.name
dropName = nearestItem.Name
```

---

## 第一步：检查参数类型

```lua
if typeof(resName) ~= "string" or typeof(dropName) ~= "string" then
	sendResult(player, false, "Invalid eat request")
	return
end
```

为什么要检查？

因为客户端不可信。

恶意客户端可能乱发：

```lua
eatEvent:FireServer(123, {})
```

服务端必须防御。

---

## 第二步：找文件夹

```lua
local folder = dropFoldersByName[resName]
if not folder then
	sendResult(player, false, "Unknown drop folder")
	warn("[EatDemo] unknown folder", player.Name, resName, dropName)
	return
end
```

如果客户端发来的 `resName` 不在允许列表里，就拒绝。

这一步很重要。

否则玩家可以乱传 Workspace 里的其他文件夹。

---

## 第三步：找掉落物

```lua
local food = folder:FindFirstChild(dropName)
if not food or not food:IsA("Model") or not food.PrimaryPart then
	sendResult(player, false, "Food not found")
	warn("[EatDemo] food not found", player.Name, resName, dropName)
	return
end
```

必须满足：

```text
1. 这个掉落物存在
2. 它是 Model
3. 它有 PrimaryPart
```

不满足就拒绝。

---

## 第四步：检查是否已经被吃

```lua
if food:GetAttribute("HasEat") == 1 then
	sendResult(player, false, "Already eaten", {
		position = food.PrimaryPart.Position,
	})
	return
end
```

如果已经被吃了，就不再加奖励。

这是防止重复吃同一个球。

---

## 第五步：检查玩家角色

```lua
local character = player.Character
local rootPart = character and character:FindFirstChild("HumanoidRootPart")
if not rootPart then
	sendResult(player, false, "Character not ready")
	return
end
```

这里用了 Lua 的短路写法：

```lua
local rootPart = character and character:FindFirstChild("HumanoidRootPart")
```

意思是：

```text
如果 character 存在，就找 HumanoidRootPart
如果 character 不存在，rootPart 直接是 nil
```

---

## 第六步：服务端重新计算距离

```lua
local rootXZ = Vector3.new(rootPart.Position.X, 0, rootPart.Position.Z)
local foodXZ = Vector3.new(food.PrimaryPart.Position.X, 0, food.PrimaryPart.Position.Z)
local distance = (rootXZ - foodXZ).Magnitude
if distance > CONFIG.EatRadius then
	sendResult(player, false, "Too far away " .. tostring(math.floor(distance)), {
		position = food.PrimaryPart.Position,
	})
	warn("[EatDemo] too far", player.Name, resName, dropName, distance)
	return
end
```

这一步非常重要。

客户端虽然已经扫描过距离，但服务端不能相信客户端。

所以服务端自己重新计算距离。

如果距离大于 30，就拒绝。

这就是服务端权威。

---

## 第七步：标记已吃

```lua
food:SetAttribute("HasEat", 1)
```

这句要放在加奖励前面。

因为这样可以尽快防止重复请求。

---

## 第八步：读取奖励

```lua
local addAttr = food.PrimaryPart:GetAttribute("addAttr") or 1
local addMoney = food.PrimaryPart:GetAttribute("addMoney") or 0
```

如果掉落物没有设置奖励，就用默认值：

```text
addAttr 默认 1
addMoney 默认 0
```

---

## 第九步：加 Muscle 和 Money

```lua
local muscle = getLeaderstat(player, "Muscle")
local money = getLeaderstat(player, "Money")

muscle.Value += addAttr
money.Value += addMoney
```

等价于：

```lua
muscle.Value = muscle.Value + addAttr
money.Value = money.Value + addMoney
```

---

## 第十步：安排体型刷新

```lua
local _, _, bodyScale, effectiveMuscle, muscleMultiplier = scheduleBodyScaleRefresh(player)
```

这里前两个返回值不用，所以用 `_` 忽略。

这个函数会根据 Muscle 变化，延迟更新玩家体型。

---

## 第十一步：播放服务端消失 Tween

```lua
local tween = TweenService:Create(food.PrimaryPart, TweenInfo.new(0.28, Enum.EasingStyle.Quad, Enum.EasingDirection.Out), {
	Transparency = 1,
	Size = food.PrimaryPart.Size * 0.2,
})
tween:Play()
Debris:AddItem(food, 0.35)
```

这会让食物球：

```text
0.28 秒内：
变透明
缩小到 20%
```

然后 0.35 秒后删除整个 food model。

---

## 第十二步：返回结果给客户端

```lua
sendResult(player, true, "+" .. tostring(addAttr) .. " Muscle", {
	kind = "eat",
	addAttr = addAttr,
	addMoney = addMoney,
	position = position,
	bodyScale = bodyScale,
	effectiveMuscle = effectiveMuscle,
	multiplier = muscleMultiplier,
})
```

这会让客户端知道：

```text
吃成功了
加了多少 Muscle
加了多少 Money
掉落物位置在哪里
当前体型是多少
当前 Muscle 倍率是多少
```

客户端收到后会更新 UI 和播放特效。

---

## 第十三步：延迟重生掉落物

```lua
task.delay(CONFIG.RespawnSeconds, function()
	if folder.Parent then
		local offset = Vector3.new(math.random(-24, 24), 3, math.random(-6, 22))
		makeDropModel(folder, offset, addAttr, addMoney, respawnColor)
	end
end)
```

8 秒后生成新的掉落物。

注意：

```lua
local offset = Vector3.new(math.random(-24, 24), 3, math.random(-6, 22))
```

这个其实不是“原位置偏移”，而是一个新的随机位置。

变量名叫 `offset`，但实际用法是 position。

更准确的名字可以改成：

```lua
local respawnPosition = Vector3.new(...)
```

# 49. 这套代码目前的几个设计问题

## 问题 1：按钮文字和实际逻辑不完全一致

客户端按钮写：

```text
2x Size
```

但服务端实际是：

```lua
muscle.Value *= 2
```

也就是永久 Muscle 翻倍。

建议改按钮文字为：

```text
Double Muscle
```

或者：

```text
Muscle x2
```

---

## 问题 2：客户端吃东西半径和服务端半径不一致

客户端：

```lua
local EAT_RADIUS = 10
```

服务端：

```lua
EatRadius = 30
```

这不是严重错误，但建议统一思路：

```text
客户端半径：负责体验
服务端半径：负责安全容错
```

如果你希望玩家靠近才吃，就可以改成：

```lua
-- 客户端
EAT_RADIUS = 10

-- 服务端
EatRadius = 12
```

这样更接近。

---

## 问题 3：客户端自动扫描自动吃，玩家没有主动操作

现在逻辑是：

```text
玩家走近球 → 自动吃
```

如果你想做模拟器玩法，这是可以的。

如果想做“按 E 拾取”，就要改成：

```text
靠近显示提示
按 E 才 FireServer
```

---

## 问题 4：UI 全部代码创建，不方便美术调整

你现在 UI 是纯代码生成。

优点：

```text
不用手动搭 UI
```

缺点：

```text
以后要改位置、样式、图片，会很麻烦
```

长期建议：

```text
StarterGui 里手动搭 UI
LocalScript 只负责找到 UI 并更新文字/绑定按钮
```

这和你之前项目里“不要代码生成 UI，方便迭代”的方向是一致的。

# 50. 你现在应该怎么学习这两个脚本

不要一口气背完整代码。按这个顺序吃透：

```text
第一层：知道客户端和服务端分别负责什么
第二层：知道 RemoteEvent 怎么互相发消息
第三层：知道客户端怎么扫描掉落物
第四层：知道服务端怎么验证和加数据
第五层：知道 UI 怎么更新
第六层：知道 Tween / Debris / Attribute / leaderstats 的作用
```

你真正要掌握的主线是：

```text
客户端发现附近有东西
  ↓
FireServer 请求
  ↓
服务端验证
  ↓
服务端修改真实数据
  ↓
FireClient 返回结果
  ↓
客户端显示和播放特效
```

这比单独记每一行代码重要得多。
