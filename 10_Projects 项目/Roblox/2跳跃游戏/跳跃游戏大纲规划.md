# 跳跃游戏大纲规划

## 当前结论

当前已经完成“训练、跳跃、领奖、返回”的基础可玩回路，不再处于只有移动原型的阶段。

距离第一版完整经济循环，还差两个主里程碑：

1. 用累计 `Speed` 派生 `Level`，并让等级真正决定最大移动速度和最大跳跃次数。
2. 完成至少一件可用 `Wins` 购买、装备并提高训练效率的鞋子，让 `Wins` 有实际消耗用途。

距离参考游戏的主要单机系统骨架，后续按六个里程碑推进：

1. Level 成长系统。
2. 鞋子与胜利商店。
3. 重生系统。
4. 踪迹系统。
5. 路线、失败处理和障碍内容。
6. 自定义速度、移动端和表现收口。

地图数量、美术资源、商品数量和最终数值平衡属于持续内容制作，不再用“还差多少个固定切片”估算。

## 核心玩法定位

玩家在跑步机训练，累计 Total Speed 并提升等级；等级提高最大移动速度和最大跳跃次数，使玩家能到达更远的平台。玩家到达平台后，可以继续挑战，也可以踩领奖区获得 Wins 并返回出生区。Wins 用于解锁鞋子和踪迹，鞋子再提高训练效率，形成长期循环。

```text
跑步机训练
→ 累计 Total Speed
→ 提升 Level
→ 提高最大移动速度和最大跳跃次数
→ 到达更远平台
→ 踩 WinReturnTrigger 领取 Wins 并返回
→ 使用 Wins 购买或装备鞋子、踪迹
→ 提高训练效率
→ 再次挑战
```

重生是后续的长期循环：达到等级要求后重置 Level 和 Total Speed，换取永久训练倍率，再从低等级重新成长。

### Level 阶段计划派生

这些值由服务器根据持久化 `Speed` 计算，不作为第二份权威存档：

- `Level: number`
- `LevelProgress: number`
- `RequiredSpeed: number`
- `MaxWalkSpeed: number`
- `MaxJumpCount: number`

`Level` 首版不单独保存。这样重进、重生和重置 Speed 后都从同一个权威值重新计算，避免 `Speed` 与 `Level` 不一致。

### 后续才考虑持久化

- `Rebirths: number`：字段名在实现前最终确认。
- 已拥有鞋子 ID 集合。
- 当前装备鞋子 ID。
- 已拥有踪迹 ID 集合。
- 当前装备踪迹 ID。

当前不保存平台进度。领奖由明确的 `WinReturnTrigger` 触发，平台识别不参与当前 Wins 结算。

## 已确认的数值基线

### 1. 单级升级需求

当前等级为 `L` 时，升到下一级所需的 Speed：

```text
RequiredSpeed(L) = floor(10 × 1.5 ^ (L - 1))
```

累计到某一级之前所需的总 Speed：

```text
CumulativeBefore(L) = RequiredSpeed(1) + ... + RequiredSpeed(L - 1)
```

当前等级进度：

```text
LevelProgress = TotalSpeed - CumulativeBefore(Level)
```

### 2. 最大移动速度

```text
MaxWalkSpeed(Level) = 5 + 3 × Level
```

- Level 1：最大移动速度 `8`。
- Level 17：最大移动速度 `56`。
- Level 22：最大移动速度 `71`。

当前第一版先让实际 `Humanoid.WalkSpeed` 等于 `MaxWalkSpeed`，保证升级后马上能看到效果。以后实现“自定义速度”界面时，再拆成：

- `SelectedWalkSpeed`：玩家当前选择的速度。
- `MaxWalkSpeed`：Level 决定的上限。

服务器必须把选择值限制在合法范围内。

### 3. 最大跳跃次数

当前采用：

```text
MaxJumpCount(Level) = Level
```

- Level 1：`Jump 1/1`。
- Level 5：`Jump 5/5`。
- Level 10：`Jump 10/10`。

这里的含义是一次离地过程中的**总可用跳跃次数**，地面起跳也消耗一次：例如 `2/2 → 1/2 → 0/2`。它不再由 Wins 直接升级。现有代码仍使用 `MaxAirJumps` 和“额外空中跳”命名；Level 接入时必须统一为这份总次数合同，并删除固定测试值依赖。

### 4. 数值回归样本

|Total Speed|派生 Level|当前进度 / 当前级需求|最大移动速度|最大跳跃次数|
|---:|---:|---:|---:|---:|
|`0`|`1`|`0 / 10`|`8`|`1`|
|`10`|`2`|`0 / 15`|`11`|`2`|
|`18,000`|`17`|`4,892 / 6,568`，UI 可显示约 `4.9k / 6.6k`|`56`|`17`|
|`124,600`|`22`|`24,874 / 49,878`，UI 可显示约 `24.8k / 49.9k`|`71`|`22`|

## 重生拟合参考规则（仅当前样本）

以下公式只对参考游戏当前观察到的 `Rebirths = 0、1、2` 样本成立，不能视为完整后期曲线：

```text
TrainingMultiplier(R) = 1 + 0.5 × R
NextRebirthLevel(R) = 10 × (R + 1)
```

|当前重生次数 R|训练倍率|显示加成|下一次重生等级|
|---:|---:|---:|---:|
|`0`|`1.0`|`+0%`|`10`|
|`1`|`1.5`|`+50%`|`20`|
|`2`|`2.0`|`+100%`|`30`|

- `[待验证]` `R > 2` 后是否继续保持线性公式。
- `[待验证]` 最终重生上限和后期倍率曲线。
- 当前参考表现是重生重置 Level 和 Total Speed，保留 Wins；真正实现前再做一次规则确认。

- 不在这一步同时写 HUD、重生或鞋子。

### A2. 服务端派生等级

- 开始实现前先确定一个唯一的服务端所有者；优先评估新增游戏业务 `LevelService`，不能让公式散落在 `SpeedService`、`JumpController` 和 HUD 中。
- 服务器读取持久化 `Speed`。
- 计算 Level、当前进度、下一级需求、最大移动速度和最大跳跃次数。
- 同步 Player Attributes，客户端只负责显示。

### A3. 接入真实移动速度

- 用 Level 的 `MaxWalkSpeed` 替换当前 `BaseWalkSpeed + Speed × 0.01` 临时公式。
- 玩家进入、Speed 改变和 CharacterAdded 时都重新应用。

### A4. 接入跳跃次数

- `JumpController` 从服务器同步的最大跳跃次数初始化和刷新 HUD。
- 把现有“额外空中跳”语义统一为“总跳跃次数”：地面起跳同样扣除一次。
- 删除对固定 `JumpConfig.MaxAirJumps` 的玩法依赖。
- Level 变化时更新最大次数；角色落地恢复到新的最大值。

### A5. Level HUD

- 显示当前等级。
- 显示 `LevelProgress / RequiredSpeed`。
- 进度条只使用服务器同步值，不在客户端自行维护另一套等级状态。

### A6. Studio 验收

- 新数据进入时显示 Level 1、`0/10`、最大速度 8、`Jump 1/1`。
- Total Speed 到 10 时变成 Level 2、`0/15`、最大速度 11、`Jump 2/2`。
- 18,000 与 124,600 的结果符合数值回归表。
- 退出重进后，只凭保存的 Speed 得到相同 Level 和能力。
- 重生角色后能力会重新应用。
- 开发面板重置 Speed 后回到 Level 1。

## 里程碑 B：鞋子与 Wins 消耗闭环

### 最小范围

- 一双免费初始鞋。
- 一双使用 Wins 购买的进阶鞋。
- 服务器验证余额、扣除 Wins、保存拥有状态和装备状态。
- 新字段写入前定义旧存档默认值、类型校验和损坏数据回退行为。
- 装备后 Studio 中能看到鞋子变化，训练获取速度也发生可验证变化。

### 设计边界

- Level 决定移动速度上限和跳跃次数。
- 鞋子提高训练效率，不直接篡改 Level 或最大跳跃次数。
- 鞋子、训练区倍率、重生倍率如何叠加，需要在实现前单独确定；当前不假设参考游戏的最终公式。

### 完成标准

```text
获得 Wins
→ 购买鞋子
→ Wins 减少
→ 装备鞋子
→ 每次训练获得更多 Speed
→ 退出重进仍保留
```

完成该里程碑后，第一版单机经济循环才真正闭合。

## 里程碑 E：路线、失败和障碍内容

- 扩展多个难度递增的平台。

平台落地识别可以继续用于日志、任务、检查点或最高到达记录，但当前 Wins 结算不依赖它。

## 风险与待确认项

- 当前 `SpeedConfig` 的旧 WalkSpeed 公式与新 Level 规则冲突，Level 接入时必须替换，不能两套公式并存。
- 当前 `JumpConfig.MaxAirJumps` 是硬编码测试值，且命名仍表示“额外空中跳”；Level 接入后必须由服务器同步的“总跳跃次数”取代。
- `Level` 不持久化，但服务器必须在 Speed 初始化和每次变化后稳定重算，避免 HUD 和角色能力不同步。
- 客户端上报落地位置目前只用于平台识别。如果以后用于奖励、任务或进度，服务器必须加强距离、平台合法性和重复上报校验。
