## 3. 游戏目标与当前核心循环

### 3.1 当前模仿目标

参考体验：

`https://www.roblox.com/share?code=72136a5a326a5941840b97b92eb851fd&type=ExperienceDetails&stamp=1783643067560`

当前以单人玩法为主，暂不展开异步竞速或下注比赛。

### 3.2 当前确定的核心循环

```text
普通走路或跑步机训练
→ 增加 Total Speed
→ Total Speed 推导 Level
→ Level 提高真实 WalkSpeed 和可用跳跃次数
→ 玩家多段跳到更远平台
→ 走进平台左侧胜利领取区
→ 增加 Wins 并传送回出生区域
→ 用 Wins 解锁鞋子、踪迹等成长内容
→ 再训练和挑战更远平台
```

### 3.3 当前玩法决策

- 地面第一次起跳免费，不消耗空中追加跳次数。
- HUD 显示的是剩余可用跳跃数：
  `2/2 → 1/2 → 0/2`。
- 落地后恢复到最大值。
- 玩家可在空中调整水平位置。
- 跳跃次数跟随 Level。
- Level 是由累计 Speed 推导的派生状态，不单独保存。
- Wins 必须由服务器增加并保存。
- 是否到过某个平台，目前主要用于平台识别/日志和未来扩展；真正领取胜利依赖独立的 `WinReturnTrigger`。
- 新玩家默认没有鞋子，普通走路基础奖励为 `+1/步`。
- 鞋子的 `+1/步` 是在基础 `+1` 上叠加，因此总计 `+2/步`。
- 跑步机是独立训练来源，普通步行也是成长来源。

## 6. 关键运行链路

### 6.1 Speed 持久化链路

```text
玩家进入
→ StorageService 自动 OpenPlayer
→ SpeedService 等待 IsPlayerDataReady
→ GetPlayerModuleData(player, "JumpGame")
→ 读取 moduleData.Speed，默认 0
→ 写入 SpeedService._speedByPlayer[player]
→ player:SetAttribute("Speed", speed)
→ SpeedController / LevelService 同时监听该 Attribute
```

增加 Speed：

```text
TrainingService 或 StepService
→ SpeedService:IncreaseSpeed(player, amount)
→ StorageService:UpdatePlayerModuleData(
     player,
     "JumpGame",
     { Speed = 0 },
     updateFn
   )
→ moduleData.Speed += amount
→ 更新服务端缓存
→ 更新 player Attribute "Speed"
→ LevelService 重新推导等级状态
→ HUD 和 Humanoid 可见变化
```

### 6.2 `moduleData` 的含义

当前玩家档案中使用游戏业务命名空间 `Modules.JumpGame`。可以把它理解成：

```lua
Modules = {
    JumpGame = {
        Speed = 0,
        Wins = 0,
    },
}
```

`moduleData` 就是其中这张 `JumpGame` 表的引用。早期默认 Schema 的 `Modules` 是空表，因此 `Speed`、`Wins` 是各业务 Service 通过：

```lua
UpdatePlayerModuleData(player, "JumpGame", defaultData, updateFn)
```

按需补入的，不需要事先在 ProfileStore 源码里定义字段。

### 6.3 Wins 链路

```text
玩家的角色零件触碰带 WinReturnTrigger 标签的 BasePart
→ WinService 解析 Character 和 Player
→ _claimingPlayers 防止 Touched 短时间重复
→ 读取触发块 Attribute "WinReward"
→ WinService:AddWins
→ StorageService 更新 JumpGame.Wins
→ 更新 Wins Attribute
→ WinController 更新 WinsLabel
→ 角色传送到 SpawnLocation 上方
```

### 6.4 Level 派生链路

```text
Speed Attribute 变化
→ LevelService 调用 LevelConfig.GetLevelState(totalSpeed)
→ 得到：
   Level
   LevelProgress
   RequiredSpeed
   MaxWalkSpeed
   MaxJumpCount
→ 写入玩家 Attributes
→ SpeedService 应用 MaxWalkSpeed
→ JumpController 使用 MaxJumpCount
→ LevelController 更新等级 HUD
```

Level 当前不单独保存。重进游戏后只要 Speed 被恢复，Level 就会重新推导。

### 6.5 跑步机训练链路

```text
CollectionService 找到 TrainingZone 标签 BasePart
→ Trigger.Touched 只接受 HumanoidRootPart
→ 识别玩家，加入该区域玩家集合
→ 设置 ActiveTrainingZone = 跑步机 Model 名
→ 客户端高亮并播放训练动画
→ 每个区域自己的循环读取：
   SpeedPerTick
   TickInterval
→ 调用 SpeedService:IncreaseSpeed
→ TouchEnded 后移除并关闭表现
```

### 6.6 普通步行链路

```text
StepService 每 0.1 秒采样 HumanoidRootPart
→ 只计算 XZ 平面的水平移动
→ 要求玩家在地面且 MoveDirection > 0
→ ActiveTrainingZone 非空时跳过
→ 过滤单次大于 12 studs 的疑似传送
→ 累积距离每达到 4 studs 算一步
→ 每步奖励：
   BaseSpeedPerStep + ShoeStepBonus
→ SpeedService:IncreaseSpeed
```

当前配置：

```text
SampleInterval = 0.1 秒
StudsPerStep = 4
BaseSpeedPerStep = 1
MaxSampleDistance = 12 studs
```

### 6.7 平台落地识别链路

为了解决服务器位置相对客户端落地状态延迟的问题，当前采用：

```text
客户端 Humanoid 进入 Landed
→ JumpController 取得客户端 HumanoidRootPart.Position
→ NetClient.FireServer(PlatformReportLanding, payload)
→ PlatformService 验证 payload
→ 从客户端上报位置向下做服务器 Raycast
→ 排除玩家 Character
→ 命中零件后沿父级向上查找带 TargetPlatform 标签的 Model
→ 输出平台识别日志
```

历史诊断发现，同一时刻客户端和服务器的角色位置曾相差约 7～10 studs，服务器第一次射线会错误命中 Baseplate。当前第一版优先完成可用功能，因此使用客户端位置作为射线起点。

边界：

- 目前平台识别不直接发放 Wins，风险可接受。
- 如果未来平台识别用于奖励、付费或排行，不能只信客户端位置，必须增加服务器距离、速度、平台范围和顺序校验。
- 当前射线向下长度曾调到约 28 studs，以兼容平台模型的底座高度；后续地图标准化后应改为配置，不应散落魔法数字。

## 7. 当前数据、Attribute 与 Remote 合同

### 7.1 持久化数据

当前实际使用：

```lua
JumpGame = {
    Speed = number,
    Wins = number,
}
```

暂未保存：

- Level：由 Speed 推导。
- MaxWalkSpeed：由 Level 推导。
- MaxJumpCount：由 Level 推导。
- ActiveTrainingZone：会话状态。
- LevelProgress：派生状态。
- ShoeStepBonus：当前只是为鞋子系统预留的运行时 Attribute。

### 7.2 玩家 Attributes

| Attribute | 类型 | 生产者 | 消费者 |
|---|---|---|---|
| `Speed` | number | SpeedService | SpeedController、LevelService |
| `Wins` | number | WinService | WinController |
| `Level` | number | LevelService | LevelController |
| `LevelProgress` | number | LevelService | LevelController |
| `RequiredSpeed` | number | LevelService | LevelController |
| `MaxWalkSpeed` | number | LevelService | SpeedService、未来 UI |
| `MaxJumpCount` | number | LevelService | JumpController |
| `ActiveTrainingZone` | string? | TrainingService | TrainingController、StepService |
| `ShoeStepBonus` | number? | ShoeService | StepService |

### 7.3 场景标签和属性

#### TrainingZone

- 标签放在每个跑步机的 `Trigger` BasePart 上。
- 每个跑步机是独立 Model，例如：
  - `Workspace.Map.TrainingZone01.Trigger`
  - `Workspace.Map.TrainingZone02.Trigger`
- Trigger 属性：
  - `SpeedPerTick: number`
  - `TickInterval: number`
- Trigger 建议：
  - `Anchored = true`
  - `CanCollide = false`
  - `CanTouch = true`
  - `Transparency` 可按调试需要设置
  - 高度覆盖 HumanoidRootPart 的运动范围

#### TargetPlatform

- 标签放在平台 Model 上，而不是放在单个零件上。
- Model 属性：
  - `PlatformIndex: number`
- `_getTargetPlatform` 会从射线命中零件逐级向父级查找带标签的 Model。

#### WinReturnTrigger

- 标签放在领奖的 BasePart 上。
- 属性：
  - `WinReward: number`
- 用户色弱，当前示例领奖块曾使用精确颜色：
  - `Color3.fromRGB(255, 128, 0)`

#### ShoeUnlockTrigger

- 标签放在鞋子 Model 下的 `Trigger` BasePart 上。
- 当前实例：`Workspace.Map.BlackShoePickup.Trigger`。
- Trigger 属性：
  - `ShoeId: string = "Black"`
  - `Anchored = true`
  - `CanCollide = false`
  - `CanTouch = true`
  - `Transparency = 1`
- `ShoeService` 只在服务器通过 `WinService:TrySpendWins` 和 `ShoeConfig.Definitions[shoeId].UnlockWinCost` 完成同次扣款、拥有权写入和后续装备；没有客户端业务 Remote。

### 7.4 Remote 名称

已知 RemoteNames 包含：

- Framework Ping
- PlayerSettings GetLanguage
- PlayerSettings SetLanguage
- `DeveloperResetSpeed`
- `DeveloperSetSpeed`
- `DeveloperSetWins`
- `DeveloperResetCharacterData`（仅 Studio 调试；不接收客户端数据字段）
- `DeveloperGrantAndEquipBlackShoe`（仅 Studio 调试）
- `PlatformReportLanding`

`PlatformReportLanding` 是客户端单向通知，走 `FireServer`，不要求返回值。  
`DeveloperResetSpeed`、`DeveloperSetSpeed`、`DeveloperSetWins`、`DeveloperResetCharacterData` 都是请求/响应，走 `Request`，返回 `NetResult`。后两者只接受 `0–1,000,000,000` 的整数，服务器分别通过 `SpeedService:SetSpeed` 和 `WinService:SetWins` 写入数据。`DeveloperResetCharacterData` 不接收客户端数值；服务器在一次 `UpdatePlayerModuleData` 内将 `Speed=0`、`Wins=0`、`OwnedShoes={}`、`EquippedShoeId="None"` 写入 `JumpGame`，再刷新 Speed、Wins 与鞋子运行时状态。

### 7.5 NetResult

成功结果：

```lua
{
    Ok = true,
    Data = ...,
}
```

失败结果：

```lua
{
    Ok = false,
    Code = "DATA_NOT_READY",
    Message = "玩家数据没有准备好",
    Data = ...,
}
```

`Code` 使用字符串是为了让程序稳定判断错误类型，不依赖显示文案。当前错误码还没有形成统一常量表，属于框架候选。

## 8. 数值策划记录

本节严格区分：

- **当前已实现公式**
- **目标游戏实测观察**
- **尚未确定的推测**

### 8.1 当前已实现的等级需求

等级 `L` 的单级需求：

```text
RequiredSpeed(L) = floor(10 × 1.5^(L - 1))
```

Speed 会逐级扣除需求来计算当前等级进度，不是简单用总 Speed 除以当前需求。

示例：

| 等级 | 升到下一级所需 Speed |
|---:|---:|
| 1 | 10 |
| 2 | 15 |
| 3 | 22 |
| 4 | 33 |
| 5 | 50 |

注意：实际代码以 `math.floor` 结果为准。

### 8.2 当前已实现的真实移动速度

```text
MaxWalkSpeed(Level) = 5 + 3 × Level
```

因此：

| Level | MaxWalkSpeed |
|---:|---:|
| 1 | 8 |
| 2 | 11 |
| 5 | 20 |
| 17 | 56 |

这与目标游戏观察“等级 1 速度 8、等级 17 速度 56”一致。

### 8.3 当前已实现的跳跃次数

```text
MaxJumpCount = Level
```

这是当前原型规则。它很直观，但高等级会产生大量空中跳，后续需要结合实际地图长度和操作体验重新评估是否封顶或分段增长。

### 8.4 普通走路和鞋子

已确认的目标游戏观察：

- 新玩家默认没有鞋子。
- 无鞋子时基础为 `+1/步`。
- 黑色鞋子标记 `+1/步`，装备后总计 `+2/步`。
- 目标游戏还观察到鞋子奖励：
  - `+1/步`
  - `+2/步`
  - `+3/步`
  - `+4/步`
  - `+6/步`
  - `+8/步`，截图中需要约 500 Wins
- 还有更高档的 `+50/步`、`+75/步`、`+100/步` 等购买内容，但暂不进入第一版。

当前实现接口：

```text
每步 Speed = StepConfig.BaseSpeedPerStep + player.ShoeStepBonus
```

因此：

```text
无鞋：1 + 0 = 1
黑鞋：1 + 1 = 2
```

### 8.5 重生观察

目标游戏截图和实测曾出现：

| 重生次数 | 显示倍率 | 下一次重生等级要求 |
|---:|---:|---:|
| 0 | ×1.00 | 10 |
| 1 | ×1.50 | 20 |
| 2 | ×2.00 | 30 |
| 3 | ×2.50 | 40 |

可能的显示公式：

```text
RebirthMultiplier = 1 + 0.5 × Rebirths
NextRequiredLevel = 10 × (Rebirths + 1)
```

但是还有一条实测：

- 玩家重生两次、装备 `+1/步` 黑鞋时，走一步观察到 `+6`。

若基础与鞋子先相加：

```text
(基础 1 + 黑鞋 1) × 3 = 6
```

这与界面可能显示的 `×2.00` 不一致，说明目标游戏还可能有额外倍率、显示时机差异或实测状态未完全清空。

结论：

- 重生倍率公式**尚未定案**。
- 不应根据一张截图直接写死。
- 实现重生前要做独立干净账号实验，分别记录：
  - 无鞋每步值
  - 有鞋每步值
  - 每个重生次数的实际增量
  - 跑步机是否也吃重生倍率

### 8.6 踪迹观察

截图中观察到：

- 橙色踪迹：约 `×1.5` 积分。
- 蓝色踪迹：约 `×1.75`。
- 绿色踪迹：约 `×2`。
- 部分踪迹可用 Wins 或其他货币解锁。

未确定：

- “积分”是否等同 Speed。
- 是否影响普通走路、跑步机或两者。
- 是否与重生倍率相乘还是相加。

因此踪迹系统必须等基础鞋子和重生公式稳定后再做。

### 8.7 大数字显示

当前 HUD 采用英文紧凑单位：

- `< 1,000`：原数值
- `1,000`：`1K`
- `1,000,000`：`1M`
- `1,000,000,000`：`1B`
- `1,000,000,000,000`：`1T`

当前先用英文，但 `HUDTextConfig` 已保留语言参数和回退入口。以后应接入现有 `Settings.Language`，而不是在各 Controller 内硬编码中英文。

## 14. YanzoFrame 框架优化候选

这些只是从 JumpGame 实战中发现的候选，不等于已经决定修改 V1。

### YF-001 Logger 业务调用位置

现状：

- `Logger.Debug/Info/Warn` 内部调用 `print/warn`。
- Studio Output 点击日志只能跳到 `Logger.lua`，不能跳到实际业务调用行。

候选：

- 研究 `debug.info` 或显式调用位置信息。
- 在日志文本中加入业务文件和行号。
- 保持 Release 下可关闭详细调用栈，避免性能与噪音。

### YF-002 日志观察与启动输出

现状：

- Registry 日志很多，业务日志难找。
- 服务端和客户端输出天然交错。
- Debug/Info 在开发期有价值，但源码跳转体验差。

候选：

- 为 scope 增加更方便的过滤。
- 提供启动摘要，减少逐条注册噪音。
- 开发模式保留详细日志，普通模式只输出摘要。
- 不承诺控制客户端/服务端全局时间顺序。

### YF-003 Storage 数据就绪协作

现状：

- 游戏 Service 自己循环等待 `IsPlayerDataReady`。
- 容易重复写等待函数。

候选：

- StorageService 提供 `AwaitPlayerDataReady(player, timeout)`。
- 或发布统一 DataReady 信号。
- 必须处理离开游戏、超时和加载失败。

### YF-004 Controller UI 就绪与超时

现状：

- `WaitForChild("GameHUD")` 曾无限等待。

候选：

- UI 加载器统一创建/挂载界面。
- Controller 使用带超时的获取接口。
- 缺失 UI 时输出明确路径和错误码。

### YF-005 通用开发者面板

目标：

- 框架层提供 Studio/白名单可见的基础面板。
- 最基础能力可包括：
  - 重置当前玩家全部测试数据
  - 查看数据就绪状态
  - 查看当前后端
  - 重新加载角色

边界：

- 具体业务按钮如 ResetSpeed 属于游戏。
- 正式服必须有权限、防误触、审计和二次确认。

### YF-006 UI 资源目录与加载

借鉴 Hotpot：

- `ReplicatedStorage.Resource.ui` 保存稳定 UI 模板。
- StarterGui 只作为编辑/调试地点或运行容器。
- 提供统一 Clone、显示、隐藏、销毁和查找机制。

需要先解决：

- Rojo 对二进制 UI 资源的工作流。
- Place 资产与源码版本同步。
- 多人客户端各自实例化。

### YF-007 每个 GUI 的独立控制脚本

借鉴 Hotpot：

- 每个 GUI 有本地、单一职责的控制模块。
- 全局 Controller 只协调业务和跨界面状态。

价值：

- 避免一个 Controller 操作大量 UI。
- UI 可复用、可单独测试。

风险：

- 小项目过早拆分会增加文件数量。
- 需要明确 GuiController 与游戏 Controller 的职责边界。

### YF-008 Service/Controller 依赖注入类型合同

现状：

```lua
self._logger = context.Logger
self._services = context.Services
```

编辑器无法可靠补全 `.Info`、`.SpeedService` 等成员，用户经常要跳到 Registry 查看 `context` 内容。

候选：

- 定义共享 `Context` 类型。
- 为 Logger、ServiceMap、ControllerMap 建立导出类型。
- Registry 构建强类型上下文。
- 评估循环依赖和类型文件维护成本。

### YF-009 统一错误码

现状：

- `DATA_NOT_READY` 等 Code 以字符串写在业务代码里。

候选：

- `ErrorCodes.lua` 或按领域拆分的错误码常量。
- 与 NetResult 类型结合。
- 文案与 Code 分离，便于本地化。

### YF-010 生命周期与 Character 清理工具

实战问题：

- Training、Step、Speed、Level 都需要监听：
  - PlayerAdded
  - PlayerRemoving
  - CharacterAdded
  - CharacterRemoving
- 容易遗漏旧连接和旧角色状态。

候选：

- 提供轻量连接清理器/Maid。
- 提供玩家与角色生命周期辅助函数。
- 不能让框架接管所有业务状态。

### YF-011 CollectionService 标签发现辅助

实战使用：

- TrainingZone
- WinReturnTrigger
- TargetPlatform

候选：

- 提供“取得某标签并按 ClassName 校验”的小工具。
- 输出统一错误日志。

边界：

- 标签名和属性合同仍属于具体游戏配置，不应硬编码进通用框架。

### YF-012 Wally 依赖映射稳定性

现状：

- ProfileStore 的 `_Index` 映射曾在 Rojo 同步时出错。

候选：

- 新项目初始化脚本自动：
  - `rokit install`
  - `wally install`
  - 检查目标依赖文件
  - 再启动 Rojo
- README 明确 ServerPackages 是生成目录。
- 加入本地诊断脚本，但不提交生成依赖。

### YF-013 派生状态更新机制

当前 LevelService 通过 Speed Attribute 再计算多个派生 Attribute。

候选：

- 明确“一项持久化主数据 → 多项派生状态”的推荐模式。
- 可能提供批量 Attribute 更新或状态快照，减少观察到一半更新的瞬间。
- 暂时不要把 Level 逻辑放进框架。

### YF-014 本地化文本接口

当前：

- 已有 `Settings.Language`。
- HUDTextConfig 预留语言参数。
- 各 Controller 仍有硬编码文本。

候选：

- 框架提供 LocalizationService 的轻量封装。
- 游戏提供自己的 key/table。
- 不让 UI Controller 直接拼接所有语言文本。

## 15. Hotpot 借鉴记录

已明确观察到：

1. 资源集中在 `ReplicatedStorage.Resource`。
2. UI 模板集中在 `Resource.ui`。
3. `ReplicatedStorage.Script.Client...Object.Gui` 下有每个 GUI 的独立脚本。
4. UI 资源和 UI 行为脚本分离。
5. 商业项目大量使用约定化目录和统一入口。

适合 YanzoFrame 的方向：

- 资源目录合同。
- UI 模板与运行时实例分离。
- 每 GUI 控制模块。
- 通用加载器和关闭/打开生命周期。
- 更明确的依赖和类型合同。

暂不照搬：

- Hotpot 的全部目录层级。
- 大量全局对象和历史兼容结构。
- 没有理解用途的包装层。
